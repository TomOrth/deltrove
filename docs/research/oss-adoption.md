# Could Deltrove become a popular open-source project?

**Research date:** 2026-10-16. This is an adoption assessment for a proposed project. Deltrove is currently planning documents only; no implementation, user base, performance results, or adoption data exist. Therefore this memo makes no probability forecast. Targets below are experiments and hypotheses, not predictions or industry benchmarks.

## Judgment

Yes, it could find a meaningful audience if it solves a sharply felt workflow problem and earns trust through interoperability and safe operation. Becoming a broadly popular general-purpose VCS is a much harder and currently unsupported claim. Anthropic explicitly says Scion itself is not a general Git replacement, fits truly enormous monorepos or very high-volume agent use, and would require migrating the surrounding lifecycle. Its suggested broader path is to add server RPC and improve sparse/shallow behavior while keeping Git. [Anthropic, “Redesigning source control at Anthropic”](https://www.anthropic.com/engineering/redesigning-source-control) Git already owns an extensive ecosystem, and replacing it means replacing far more than object storage: editor workflows, CI, hosting, identity, review, release automation, migration, and team habits all need to keep working.

Do not position “agent workspaces” or parallel agents as the wedge by itself: GitButler already documents parallel agent work in a shared Git workspace, with explicit tradeoffs against separate worktrees. [GitButler parallel agents](https://docs.gitbutler.com/ai-agents/parallel-agents) A more defensible experiment is a **server-side source-data access layer for CI and developer tools that answers history, diff, ancestry, and selected-file queries without each job provisioning and maintaining a full local repository**, while retaining Git as the system of record. If evidence supports a deeper server-authoritative format later, that can be a second-stage migration.

Keep the project Apache-2.0 and make the core usable without a paid or source-available service. Optional adapters can have separate licenses and build boundaries, but no core operation, self-hosted installation, or user data path should depend on Restate or another source-available component. The repo already distinguishes the Restate BSL server from its MIT SDK; preserve that separation in product packaging and communicate it plainly.

## What the adoption examples suggest

| Example | Primary-source evidence | Lesson for Deltrove |
| --- | --- | --- |
| Jujutsu (`jj`) | Its documentation describes Git compatibility and a Git backend; it is explicitly designed to improve the VCS experience while using Git repositories. [Jujutsu docs](https://jj-vcs.github.io/jj/latest/), [Git compatibility](https://jj-vcs.github.io/jj/latest/git-compatibility/) | A new command model can be tried with lower switching cost when repository format and remotes remain Git. This is the strongest adoption bridge to study. It does not prove a new server format can attract teams. |
| Fossil / SQLite | SQLite publishes why it chose Fossil, and provides a read-only Git mirror because Git users expect the standard interface. It notes that Fossil and Git identify commits differently. [SQLite: Why SQLite Does Not Use Git](https://www.sqlite.org/whynotgit.html) | A vertically integrated alternative can work for a committed project with a distinctive workflow and a maintainer who owns the whole experience. Even an established project maintains a compatibility path for outsiders. |
| GitHub importer | GitHub reported more than 400,000 repositories had used its importer in 2016; in 2023 it announced ending non-Git repository imports due to very low usage. [Importer announcement](https://github.blog/news-insights/product-news/migrate-your-code-with-the-github-importer/), [deprecation notice](https://github.blog/changelog/2023-04-16-deprecation-importing-non-git-repositories-with-github-importer/) | Migration demand can exist but decays; an easy migration tool alone is not ongoing product pull. Measure continued use after migration. |
| SourceHut | SourceHut's own second-year alpha account reported thousands of Git and Mercurial repositories, and a bundled set of collaboration services. [SourceHut 2020 report](https://sourcehut.org/blog/2020-11-15-sourcehut-2-year-alpha/) | An independent hosting ecosystem can accumulate users by being opinionated and integrated. This is a vendor-reported snapshot, not evidence that a VCS backend alone caused adoption or that its model transfers. |

These examples are not controlled comparisons. They suggest that the winning product is usually a complete workflow or a low-friction overlay, not a novel object database on its own.

## Adoption barriers to treat as product requirements

**Git compatibility and migration.** Teams have years of history, tags, signatures, submodules, LFS objects, hooks, and automation. Git's own format documentation says clients that do not understand a repository format extension must not operate on it, to avoid incorrect results or data loss. [Git repository layout](https://git-scm.com/docs/gitrepository-layout) Git's hash transition documentation describes compatibility translation as a multi-step project, not a trivial export. [Git hash-function transition](https://git-scm.com/docs/hash-function-transition) Deltrove should publish a supported-feature matrix, preserve source identities and provenance through import/export where possible, and provide a dry-run, verification, and rollback path. Initially, one-way Git ingest and a useful read/export path are safer promises than transparent bidirectional fidelity.

**CI and editor integration.** GitHub Actions' standard checkout workflow and VS Code's built-in source control start from Git repositories; VS Code explains that its built-in Git integration uses the installed Git distribution, while other providers need extensions. [GitHub Actions checkout](https://github.com/actions/checkout), [VS Code source control](https://code.visualstudio.com/docs/sourcecontrol/overview), [VS Code provider FAQ](https://code.visualstudio.com/docs/sourcecontrol/faq) That means each non-Git workflow creates integration work for the project and its users. First deliver one CI adapter with clean artifact/status reporting and a documented way to build from a changeset. Do not count “we have an API” as CI integration.

**Trust and recovery.** Source control holds valuable work and is in the critical path of every change. A server-authoritative model increases the perceived blast radius of outages, account problems, or bugs. Before inviting production use, demonstrate independent backups, restore drills, integrity checks, export at any time, explicit acknowledgement/durability semantics, and recovery of local uncommitted work. A polished demo cannot substitute for evidence that a failed server or migration cannot strand the team's work.

**Offline and local-first expectations.** Git keeps history and many operations locally. A server-authoritative system trades that autonomy for shared state, access control, and centralized review. The CLI should support safe local edits plus cached status and diff while disconnected, and clearly report that canonical commits and landing require the server. Preserve local edits across disconnects and restarts, then surface conflicts on reconnect; do not queue commits for later offline publication. Avoid implying that this model is a universal Git replacement.

**Installation and operation.** A self-hosted small-team MVP needs a short, reliable install path, upgrades, backup/restore, diagnostics, and modest resource needs. Fossil's primary account emphasizes its standalone binary and simple server as part of its appeal; that is a useful bar for friction, not a benchmark for this Rust/PostgreSQL design. [SQLite/Fossil rationale](https://www.sqlite.org/whynotgit.html) A Compose quickstart is a reasonable first target, but maintainers should test it from a clean machine and document storage, TLS, identity, and upgrade responsibilities.

## Contributor appeal and maintainer sustainability

The Rust + PostgreSQL + immutable-object design is credible for systems contributors interested in correctness, storage, and developer tools. It is also a high entry cost: Rust server internals, protocol semantics, client behavior, database operations, and web review make a broad surface area. A small core team can be overwhelmed by feature requests across all those layers before any one workflow is excellent.

Make contribution possible before asking outsiders to own production-critical internals: publish a local demo, a protocol and object-format overview, a working dev setup, fixtures, a short “good first issue” path, and precise subsystem ownership. Prefer small, independently reviewable boundaries such as CLI commands, import fixtures, web review polish, CI adapters, docs, and operational packaging. Keep core data invariants and migration logic under close maintainer review until the compatibility suite is mature.

Apache-2.0 is a straightforward permissive project license, but “open source” alone does not provide ongoing maintenance capacity. A VCS has unusually high expectations for correctness and long support horizons. Budget explicitly for security reports, release signing, supported platforms, database/storage upgrades, backup compatibility, dependency CVEs, migration bugs, and user support. Before broad launch, decide who owns releases and security response, what versions receive fixes, and how project-owned infrastructure will be funded. If a paid hosted offering is later considered, make self-hosting and data export remain first-class and keep commercial services out of the core license boundary.

Avoid selecting an orchestration dependency for its conceptual fit alone. The project plan compares PostgreSQL workers, Temporal, and Restate in a bounded evaluation, then selects an implementation for the supported lifecycle; reusable domain commands are the stable boundary, not a promise that every engine remains supported through a permanent adapter framework. Keep a self-hostable OSS install path regardless of the engine decision. Restate's BSL-licensed server merits an explicit distribution review before adoption; its open-source SDK does not change the server license. [Restate repository and license](https://github.com/restatedev/restate), [Restate SDK](https://github.com/restatedev/sdk-rust)

## A differentiated wedge to validate

Candidate positioning: **“A self-hosted source-data service for CI and developer tools: query Git history and fetch just the source data a job needs, without maintaining a full clone for every job.”** This follows Anthropic's own suggestion that server-side RPC can improve Git without replacing it, and its report that Scion initially served metadata queries before introducing a new client, format, and protocol. Anthropic's extreme checkout and merge-rate figures describe its exceptional internal environment, so they do not establish that ordinary teams have the same problem. [Anthropic report](https://www.anthropic.com/engineering/redesigning-source-control) Test a narrower, cheaper-to-adopt problem first. Possible proof points are:

- A CI worker gets diff, merge-base, path history, or blame through a documented API and fetches only needed files; measure job setup time, bytes transferred, clone/cache maintenance, and failure rate against current Git mirrors, partial clones, and provider APIs.
- A self-hosted installation can cache immutable source data, enforce repository access, and export/serve ordinary Git data so teams can try the service without moving their canonical repo.
- Only if those queries show repeat use should the team test sparse workspaces and eventually authoritative server-side commits/review. Measure developer edit latency and recovery/offline impact separately from CI savings.

Treat these as hypotheses, not established differentiation. Git already has sparse checkout, partial clone, shallow clone, and promisor remotes; Anthropic says it used these and internal mirrors before deciding that its particular mirror operations no longer scaled. [Git docs](https://git-scm.com/docs) Deltrove must benchmark against those existing options and show a measurable benefit in a repeatable workload. If a server-side query layer is enough, do not build a new authoritative VCS. If it does not beat existing Git hosting or cache approaches, abandon this wedge.

## Staged validation and launch experiments

1. **Problem interviews, before broad implementation.** Talk with 12–20 engineering teams who plausibly feel monorepo, CI-workspace, or self-hosting pain. Ask about their last concrete incident, workarounds, minutes and machine resources spent, and who would approve a pilot. Hypothesis: at least 5 describe the same frequent, costly problem and at least 3 volunteer a representative repository/workflow. These numbers are screening gates chosen for this project, not validated market thresholds.
2. **Metadata-query prototype on Git data.** Build a limited API or adapter around one real repository and one CI/tool workflow. Compare existing Git clone/cache/partial-clone patterns and provider APIs against the server-side path for job setup time, transferred bytes, cache/mirror maintenance, latency for history/diff/ancestry queries, and failure behavior. Keep the workload, baseline, and scripts public. Hypothesis: repeated query workloads show a material improvement in one pre-agreed cost while remaining easy to turn off and retaining Git export. Stop or narrow scope if current Git or hosting APIs match it adequately.
3. **Design partners and self-hosted alpha.** Recruit 3–5 teams to install their own instance and use it against a non-critical or mirrored repository for 4–8 weeks, starting with one CI/tool integration. Provide integrity checks, restore rehearsal, Git export, and a clear off-switch. Observe repeated weekly query volume, jobs served, latency, failed queries, maintenance minutes saved/spent, and whether the integration remains enabled. Hypothesis: at least 3 teams complete setup and at least 2 retain the integration through the final four weeks, with measured recurring usage. Only then recruit a separate small test of sparse workspaces/server-authoritative commits. Do not call an import or star “adoption.”
4. **Public beta only after the trust gate.** Publish signed Linux/macOS CLI releases, repeatable self-host deployment, import/export documentation, compatibility fixtures, a security contact, issue triage expectations, and release/support policy. Offer an opt-in telemetry path plus a manual pilot check-in; do not collect repository content. Report aggregate retention and failure rates with definitions, not just GitHub stars.
5. **Post-launch check at 90 days.** Evaluate monthly active teams and contributors, 4-week and 12-week team retention, workflows per retained team, activation time, successful upgrade/restore rates, issue response time, number of independent contributors who complete a merged change, and maintainer hours per active team. Stars, downloads, page views, and sign-ups are discovery signals; none alone demonstrates value.

### Proposed go/no-go hypotheses

Proceed to a public beta if the alpha has at least 3 independent teams, 2 retained weekly teams over the final month, a repeatable onboarding path, a successful backup restore and Git export for every pilot, and no unresolved data-integrity issue. Continue investment after public beta only if by day 90 at least 5 teams remain active monthly, at least 3 show 12-week retention, and support/release work fits capacity the maintainers have explicitly committed. If these gates miss, interview churned teams and narrow the use case; do not inflate success with stars or imports. These thresholds are deliberately modest, falsifiable project hypotheses, not forecasts or universal benchmarks.

## Sources and limits

The cited adoption examples are primary project or platform sources. They establish documented product facts and self-reported activity, not causal evidence about why users chose a tool. The proposed positioning, experiments, and numerical gates are Deltrove recommendations and hypotheses. No user research, implementation trial, benchmark, or market-size analysis has been conducted for this memo.
