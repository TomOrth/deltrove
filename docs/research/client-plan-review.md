# Client and frontend review of the technical plan

Reviewed `docs/technical-plan.md` against `docs/research/clients-and-frontend.md` and the cited primary documentation, 16 October 2026. This is a planning review only; the technical plan was not edited. I found no fundamental contradiction with the user's direction, and the plan is unusually careful about not promising Git compatibility, VFS behavior, or scale based on Anthropic's report. The items below are concrete changes that would make the plan easier to execute and less likely to imply unsupported guarantees.

## Material changes recommended

1. **Narrow what counts as the self-hostable MVP and protect the timeline.** The MVP currently combines native immutable history, sparse workspaces, a web repository browser and review, comments/approvals/checks/landing, CI integration, Git import and export, backup/restore, quotas, and a compatibility inventory. Yet the roadmap allocates phases 1–4 only 12–15 weeks after feasibility, before the 3–5 week pilot. For 2–4 engineers, this is a high-risk estimate even with existing auth/CI. Keep a vertical product slice: import a bounded Git corpus; browse/history/diff; sparse local edit/status/diff; online server-authoritative commit; one simple review/land path; and tested backup/restore. Defer advanced approvals, multiple CI adapters, broad Git round-trip fidelity, and scale-specific cache/index work until the core end-to-end slice works. If the listed feature set is intentional, label the 16–22 weeks as a best-case pilot hypothesis and add explicit scope cuts/contingencies rather than presenting all features as phase deliverables.

2. **Make cache/daemon timing consistent.** The opening stack calls out an “eventual cache daemon,” while sections 6 and 10 correctly describe it as a later/optional extraction. The client memo recommends an in-process cache behind interfaces first. Align the opening stack and diagram wording with that: one CLI process owns its local cache/workspace in MVP; a per-user/node daemon is a later scale option after request coalescing, cache sharing, and lifecycle needs are measured. Do not imply that a node daemon or per-user daemon ships in the initial self-hostable install.

3. **Clarify snapshot freeze during server commit.** Resolved semantics: a native changeset is created with the workspace's explicit parent, so an outdated main tip does not itself block commit; landing remains a separate target-ref compare-and-swap. Make that explicit in the CLI example and ensure the client freezes a selected-file snapshot before upload. Edits made after freeze must remain as dirty changes for the next commit, while retries with the same request ID must refer to the same frozen payload. Define `sync` as fetch/reconcile and say when a two-parent merge is an explicit command. This prevents users from reading Git-like commands as Git-equivalent operations. The client memo now reflects the explicit-parent and freeze semantics.

4. **Keep the Git migration claim explicitly corpus-bounded until round-trip evidence exists.** The migration section does a good job preserving raw source objects and spelling out special refs, signatures, filters, submodules, LFS, and `.git` integration caveats. The top-level MVP bullet “resumable Git ingestion and tested one-way export with a published compatibility matrix” should clarify that initial compatibility is a declared subset tested against named repositories and fixtures, not generic Git round-trip. Include a golden round-trip comparison for source objects, refs, modes, byte paths, parent order, tags and supported special refs. Preserve raw objects where exact original OIDs/signatures are claimed; generated native commits necessarily receive new Git identities. Git's own plumbing docs describe these as interchange mechanisms, not an automatic lossless VCS migration: [fast-export](https://git-scm.com/docs/git-fast-export), [fast-import](https://git-scm.com/docs/git-fast-import), and [cat-file batch](https://git-scm.com/docs/git-cat-file).

5. **Make the platform promise match phase 2.** Linux/macOS first with Windows follow-on is a reasonable small-team tradeoff and is supported by the filesystem cautions in the client memo. Put that limit in the top-level product requirements and release artifact matrix, and state that Windows repositories are not supported until the follow-on tests pass. The existing invariant tests should still run on all three operating systems before a general availability claim; Go's `os.Rename` explicitly notes non-Unix non-atomic behavior ([Go `os.Rename`](https://go.dev/pkg/os/?m=all%2Cold#Rename)), and Rust similarly documents platform-dependent rename semantics ([Rust `fs::rename`](https://doc.rust-lang.org/std/fs/fn.rename.html)). The plan's journal/recovery design is the correct response; do not promise a uniform atomic multi-file checkout.

6. **Add frontend security and interaction checks to the frontend gate.** The plan already says to escape repository filenames/source and not execute repo HTML/SVG/Markdown HTML, but the validation table does not name XSS fixtures or session/CSRF checks. Add hostile filenames, source snippets, comment bodies, and Markdown links to browser tests; verify session cookie attributes, CSRF behavior, same-origin authorization, and that cached private-object responses still authorize. Keep the local workspace explicitly outside browser scope, as the plan does. The W3C ARIA practices require authors to supply keyboard behavior for custom widgets; retain keyboard and accessible unified diff tests ([WAI-ARIA APG](https://www.w3.org/WAI/ARIA/apg/)).

## Language and stack notes

The Go default is internally coherent with a small-team self-hostable service plus cross-platform CLI, and the plan properly labels the ranking as judgment rather than benchmark. Rust is also a coherent full-stack alternative when maintainer expertise supports it; avoid a mixed Go/Rust implementation in the MVP. The user's exclusion of C/C++ is recorded clearly.

The alternative rows need only small factual refinements:

- **Swift:** “smaller project-specific ecosystem” is an inference, not established by the linked Swift-on-Server page. Keep it explicitly as a team/package-matrix judgment. Swift officially supports macOS, Linux and Windows, and documents a static Linux SDK; mention that build/deployment artifacts are platform-specific and Windows setup has extra toolchain requirements if this alternative is being compared seriously ([Swift platform support](https://www.swift.org/platform-support/), [static Linux SDK](https://www.swift.org/documentation/articles/static-linux-getting-started.html), [Windows install](https://www.swift.org/install/windows/)).
- **Zig:** “cross-compilation possibilities” should not sound like equal support for every target. The official support table has tiers and target-specific standard-library/toolchain support; link it and say to inspect actual release targets ([Zig platform support](https://ziglang.org/learn/platform-support/)).
- **C#/.NET:** The table's AOT caveat is correct but could make the packaging tradeoff precise: single-file deployments are still OS/architecture-specific; Native AOT has feature constraints and no cross-OS compilation ([.NET deployment](https://learn.microsoft.com/en-us/dotnet/core/deploying/), [AOT cross-compilation](https://learn.microsoft.com/dotnet/core/deploying/native-aot/cross-compile)).

Java/Kotlin is a legitimate optional alternative for an existing JVM team, but it is not needed in the initial decision memo if the user specifically asked to compare Go/Rust and other systems-oriented choices. If retained, keep it clearly marked as an ecosystem/team preference rather than a systems-language equivalent. The current exclusions and top-level Go recommendation otherwise make sense.

## What already looks sound

The plan distinguishes sparse omission from deletion, protects dirty scope changes, specifies a journal with preimages and recovery, avoids claiming filesystem-wide atomic rename, makes watchers advisory, keeps shared daemon IPC out of MVP, avoids a real VFS, and specifies online server commits with offline local edits/status/diff. It also distinguishes custom native APIs from Git smart-HTTP/`.git` compatibility, calls for preservation of raw Git objects, treats cache authorization separately from object possession, and recommends server-produced/lazy-loaded diffs with an accessible unified mode. These points align with the primary docs and the client memo; they should remain explicit through revisions.

The plan's status/diff and workspace safety gates are appropriately concrete. One addition worth making is a restart/offline fixture: disconnect, edit several materialized files, restart the CLI, verify status/diff and dirty recovery, reconnect to a moved server head, and confirm clean reconciliation or a preserved explicit conflict without loss. No queued offline commit should appear in that test.
