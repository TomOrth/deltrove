# Temporal for Open Scion: durability and orchestration assessment

**Checked:** 16 October 2026. **Scope:** Temporal only; research, no implementation. The companion comparison is responsible for DBOS. This memo checks the project’s [technical plan](../technical-plan.md) and [Rust backend scaling plan](../rust-backend-scaling.md).

## Finding

Temporal is now a credible Rust option for durable, long-running orchestration. The old “Rust SDK is preview” conclusion is stale: Temporal announced general availability on 4 September 2026, published SDK v1.0 that day, and its official release page lists v1.1 on 6 October. The v1.1 notes include fixes and version-routing features, so GA should not be read as “no ongoing SDK changes.” The SDK repository is MIT-licensed. Its README still marks selected API/features experimental; pin a release and keep experimental APIs out of the adoption case unless separately accepted. [GA announcement](https://temporal.io/changelog/rust-sdk-generally-available), [official release history](https://github.com/temporalio/sdk-rust/releases), [Rust SDK README and crate features](https://github.com/temporalio/sdk-rust/blob/main/crates/sdk/README.md), [SDK license](https://github.com/temporalio/sdk-rust/blob/main/LICENSE.txt).

Temporal adds a durable execution engine, not transactional VCS storage. A Workflow’s event history lets a Worker replay deterministic decisions after restart and resume timers/messages. Activities perform external work and may be attempted more than once when a worker fails between making an effect and recording its result. The API can feel “effectively once” while Activity attempts remain at-least-once; database writes, object publication and CI launches still need idempotency keys, compare-and-swap, deduplication, or fencing. The docs explicitly distinguish workflow replay from activity execution and require deterministic workflow code; code changes need compatible replay and a version rollout strategy. [Task execution](https://docs.temporal.io/tasks), [workflow determinism and versioning](https://docs.temporal.io/workflow-definition), [Activity failure/retry behavior](https://docs.temporal.io/encyclopedia/detecting-activity-failures).

Self-hosting does **not** inherently require Cassandra. Temporal’s open-source server supports SQL persistence with PostgreSQL (and MySQL); SQL Visibility is supported on PostgreSQL 12+ for server versions 1.20+. It is a separate Go service with its own persistence, Visibility configuration, schema upgrades, history-shard sizing, monitoring, TLS/auth hardening, and restore/HA operations. The service docs say `numHistoryShards` is fixed after first start. The Rust SDK uses gRPC to this server. Temporal Cloud avoids operating that service but adds a hosted dependency and commercial terms. The server and SDK are open-source MIT projects. PostgreSQL can be the chosen backend, but Temporal records and application domain records are not one atomic transaction simply because they use PostgreSQL. [Self-hosted service configuration](https://docs.temporal.io/references/service-configuration), [Visibility database support](https://docs.temporal.io/visibility), [production deployment choices](https://docs.temporal.io/production-deployment), [server license](https://github.com/temporalio/temporal/blob/main/LICENSE).

## Where it fits

Temporal best fits workflows that span process restarts or deploys, wait on people or external systems, or require durable multi-step retries. That maps well to exact-candidate CI/check orchestration, review/approval deadlines and reminders, resumable import with checkpointed batches, and expensive derived-index build/rebuild pipelines. Workflow signals/updates can accept approval and cancellation as durable messages; Activities can launch CI or run a bounded import/index unit and record results. Workflow state should orchestrate these operations; PostgreSQL remains authoritative for candidate identity, review/check records, policy, refs and CAS.

It is a poor reason to move the hot path. Do not put each blob frame, object read, changeset write, manifest lookup, or short ref update through a Workflow. Keep immutable objects and metadata in the existing object-store/Postgres design; keep small jobs in the proposed fenced Postgres queue unless measurements show concrete value from Temporal’s retry history, timers, message handling or visibility. Temporal does not create atomic commit across PostgreSQL and S3, serialize a hot ref correctly by itself, prove a CI result belongs to the current candidate, or eliminate the need for the existing fenced claims and exact-candidate checks. Its benefit is durable coordination around those invariants, not replacement of them.

The integration itself has a crash gap: a DB transaction cannot atomically commit a domain mutation and start a Temporal Workflow through gRPC. For reliable dispatch, write an application outbox row in the same Postgres transaction as the durable domain state, then have a dispatcher retry Workflow start using a stable, domain-derived Workflow ID. If the start succeeded but the response was lost, retry with the same identity and reconcile “already started” to that operation. Do not claim accepted work until it is durably represented in the domain DB/outbox. A later cancellation is also a request, not rollback: workers must check current candidate/status and fencing tokens before publishing results; cancellation can race a completed external side effect. Temporal’s official docs describe retry and idempotency requirements for retried operations. [Activity execution semantics](https://docs.temporal.io/tasks), [Temporal operation idempotency](https://docs.temporal.io/nexus/operations).

Long-lived review workflows also introduce event-history retention and replay compatibility obligations. Keep workflow inputs/outputs small and avoid copying patch contents, blobs, tokens or unbounded logs into history. Store durable application data in Scion and pass identifiers. Workflow code must use deterministic workflow APIs for time/randomness and route I/O through Activities; adding/removing workflow commands in a deployed version can make an old execution nondeterministic. Adopt worker versioning or a tested compatibility/patching process before workflows span releases. [Rust workflow restrictions](https://github.com/temporalio/sdk-rust/blob/main/crates/sdk/README.md), [workflow versioning](https://docs.temporal.io/workflow-definition), [worker deployments/versioning](https://docs.temporal.io/best-practices/worker).

## Failure tests and adoption gates

Before making Temporal an MVP dependency, prove these behaviors in an integration spike using the pinned Rust SDK and the intended self-hosted Postgres-backed service (or document the Cloud deployment choice):

1. Commit candidate/check state plus outbox, crash before dispatch, restart, and verify one logical workflow starts. Simulate successful start with a lost response; dispatch again and verify it attaches to the same workflow identity.
2. Kill an Activity after it writes SQL or publishes an immutable object but before Temporal records completion. Let it retry; prove idempotency prevents duplicate logical publication and fencing/CAS prevents stale ref advancement.
3. Cancel or supersede a candidate while CI/import/index work is active; deliver late Activity completion and prove a transactional current-version check rejects stale publication. Exercise the reverse race where external CI succeeds just before cancellation.
4. Restart workers and the Temporal service during timers, signals, retries and a multi-batch import; verify no acknowledged application state disappears, checkpoints resume safely, and operator-visible queue/workflow state is sufficient to reconcile uncertain outcomes.
5. Replay representative open workflow histories against the proposed upgrade, test old/new worker rollout and rollback, then rehearse service database backup/restore and retention. Include payload limits, history growth, workflow-ID reuse, task-queue backlog and Postgres connection/WAL contention in the capacity check.

**Recommendation:** Do not require Temporal for the self-hostable MVP. The existing Postgres outbox/queue design already gives this product durable jobs with leases, fencing, bounded workers and no extra production service; the current plan explicitly has no measured workload demonstrating a gap. Keep an integration seam around job dispatch and state machines. Revisit Temporal when a measured need appears for long-lived approval/check coordination, durable timers/signals, complex multi-step recovery, or operational visibility that becomes more expensive to implement and audit in the application queue. For an enterprise deployment that already runs Temporal or accepts Temporal Cloud, use it selectively for those orchestration flows while retaining Scion’s Postgres/ref/object-store transaction rules. It is not an ACID-compliance shortcut and should not be added to enterprise architecture solely as a scale signal.

This recommendation changes only if the failure tests show the existing queue cannot meet concrete recovery or operations requirements, or if a target customer requires integration with its Temporal platform. If adopted, gate rollout on pinned stable Rust APIs, history replay/version compatibility, outbox/idempotent start, idempotent Activities with fencing, explicit retention/payload policy, service restore drills, and measured cost/latency under the actual CI/import workload.
