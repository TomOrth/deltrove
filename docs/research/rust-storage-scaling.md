# Rust storage and metadata scaling memo

**Date:** 16 October 2026\
**Scope:** Rust server, with the Go CLI choice unchanged. Research only; no prototype or performance results are implied. This memo narrows the storage/metadata questions in `technical-plan.md` and the earlier `backend-stack.md`.

## Recommendation

Keep the proposed storage contract for the first Rust server: PostgreSQL is authoritative for mutable refs, authorization, reviews, landing state, idempotency records and outbox; immutable file bytes and large immutable payloads use repository-scoped, content-addressed object keys. Upload and verify bytes before a short SQL transaction publishes references to them. Derived manifests and graph accelerators are rebuildable and never authorize writes. Rust does not change the cross-store crash, GC, or consistency requirements.

Start with one Postgres primary and one object-store adapter, and make API and derivation worker concurrency separately bounded. Use conditional ref updates and short transactions; parallelize independent changeset validation and manifest work, while preserving serialization for updates to the same ref and ordered landing queue. Scale measurements should distinguish database saturation, derivation backlog, object-store throughput, and per-ref queue delay. Splitting customers across primaries can relieve aggregate load across repositories, but cannot split the hot portions of one repository or make one ref update concurrent.

For SQL, spike **SQLx first** with `PgPool`, explicit SQL, migrations, and compile-time checked queries for stable statements. It provides PostgreSQL support, async pooling, prepared statement caching and streaming; its query macros validate SQL against a development schema at build time, with offline metadata available for builds that should not need a live database. This is a good fit for a relational service with many transactional invariants and no need to hide SQL behind an ORM. Pin and evaluate a released version at project setup; current `latest` documentation can move independently from the release selected for production.

Keep **`tokio-postgres` plus `deadpool-postgres`** as the concrete alternative. `tokio-postgres` is an async, pipelined Postgres client and deliberately leaves pooling to a companion crate; `deadpool-postgres` supplies a managed pool and statement cache. Prefer this route if its lower-level connection, pipelining, or TLS behavior better fits the implementation, or if SQLx compile-time query analysis becomes a material build/schema workflow burden. Neither driver removes the need to implement transaction retries, explicit CAS predicates, idempotency, and lock ordering correctly. Do not choose on speed claims: compare both against the same schema and workload if that choice becomes consequential.

For object storage, evaluate Apache Arrow's Rust `object_store` crate as the first adapter candidate. It has async APIs for local files and cloud stores, including S3, and exposes conditional operations, multipart upload, ranges and bulk deletion. Its interface is a useful integration boundary, not proof that every S3-compatible service has equivalent preconditions, durability, or consistency. The adapter contract suite must run against each actually supported provider; keep GC and reference publication logic in the application layer.

## Data layout and growth boundaries

Use the format direction already captured in the plan: immutable changesets encode ordered parents and canonical first-parent-relative operations; the derived snapshot is a versioned, content-addressed tree. Preserve arbitrary parent edges in canonical metadata. A basic relational graph should start with indexed `(repo_id, changeset_id)` records and ordered parent-edge rows. Keep correctness queries bounded; add generation numbers, skip pointers, or other reachability accelerators only after representative ancestry and merge-base workloads demonstrate a need. These are derived data and must be reproducible from canonical records.

Do not represent each revision as a copied flat manifest. Prototype a persistent, paged directory map: each directory/page is immutable and content addressed, and a change writes changed leaf pages and their ancestors while sharing unchanged pages. This bounds ordinary changes by the changed paths and tree depth, subject to page splits and hot directories; it is not a guarantee until measured. Keep path-byte ordering and tree semantics fixed separately from page layout. A million-entry directory with one-file updates is the critical format experiment from the plan. Persist a complete snapshot root per ready changeset so file/tree reads do not replay the complete changeset history. If a path-query index in Postgres is added, treat it as an accelerator keyed by repository, snapshot/changeset and derivation version, and gate reads on its readiness state.

Store compact, query-critical metadata in Postgres; avoid large serialized trees or file bytes in rows. Start with repo-scoped indexes and schema keys even when a deployment has one database. This keeps the eventual placement boundary clear. Partition large append-only event/audit data only when query and retention measurements justify it; PostgreSQL partition pruning depends on queries matching the partition key and adds planning and maintenance considerations. Partitioning a table is not equivalent to distributing one repository's transactions across machines.

Single hot monorepos are different from many independent repos. Many repos allow sharding by tenant/repository and provide substantial independent concurrency. A single large repo stresses tree derivation, path/history indexes, graph traversals, ref serialization, landing queues, retention/GC scans and cache locality. Keep repository-wide work out of commit transactions; use resumable background jobs with bounded work and visible readiness. A hot protected ref remains a deliberate queue, especially when required checks must run against the latest target. Faster metadata storage alone cannot eliminate this product-level serialization rule.

## Pooling, workers and durability boundaries

Give the API and workers separate semaphores or pools for database connections, CPU-heavy graph/merge work, and object-store requests. Set database pool limits from the total across all replicas and operational/admin connections, not independently per process. Bound acquisition waits and queue depth, expose pool wait/usage metrics, and avoid holding a SQL connection while uploading blobs, waiting on CI, doing large graph scans, or streaming an object to a client. Stream object bytes with bounded buffers and cancellation propagation. Use bulk SQL operations where they reduce round trips without making transactions unbounded.

Keep the existing transaction recipe: object writes complete and hashes are verified before SQL publication; SQL atomically publishes the changeset, graph rows, retention pin, outbox and idempotent result. Object writes can leave garbage, but committed metadata must not point to absent objects. Workers claim leased outbox tasks and are idempotent. GC needs explicit upload reservations, publication/mark fencing, backup watermarks and a recheck before deletion; object-store lifecycle deletion must remain off until concurrent publish and restore experiments pass. Rust ownership helps control in-process aliasing and buffer lifetimes, but it does not establish these distributed invariants.

## Distributed metadata candidates

Do not add FoundationDB or TiKV to the MVP. Evaluate them only if traces show that one repository's metadata workload—not file transfer or compute-heavy derivation—is outgrowing the measured PostgreSQL envelope and independent repository sharding is insufficient.

FoundationDB is an ordered transactional key-value store, so adopting it means designing keyspaces, secondary indexes, relational joins, pagination and operational tooling explicitly. Its current documentation states a 10,000,000-byte transaction limit, recommends redesign when transactions exceed 1 MB, limits keys to 10,000 bytes and values to 100,000 bytes, and does not support transactions longer than five seconds. These constraints fit compact bounded metadata transactions better than storing manifests or large batches in a single transaction. The Rust `foundationdb` crate wraps the FoundationDB C API and requires the FoundationDB client to be installed; its documented platform tiers are strongest for Linux x86_64. This is a deployment/library constraint to include in an evaluation, not a reason to exclude it.

TiKV exposes transactional MVCC and raw KV APIs through a Rust client, and the client documentation explicitly warns against using both APIs on the same keyspace. It also brings Placement Driver, region placement, cluster operations and distributed retry semantics. Treat transactional API support and compatibility as version-pinned gates, and model refs/reviews/outbox transactions before calling it a Postgres replacement. Neither candidate avoids the serialization point on an individual mutable ref.

An evolution path could keep Postgres for account, identity and review data while moving only a demonstrated high-volume repository metadata domain. But this creates cross-store transaction and recovery boundaries and is not a default recommendation. First decide whether a single-repository limit is actually caused by Postgres and which rows/indexes must be transactionally colocated. If refs, policy and landing state need cross-domain atomicity, a partial move may add more correctness burden than capacity.

## Experiments and decision gates

Run these as comparative experiments after a thin implementation exists; there are no results yet.

1. **Driver/pool spike:** implement the same ref-CAS and outbox transaction in SQLx and `tokio-postgres`/Deadpool. Compare schema/migration workflow, query ergonomics, prepared statement behavior, cancellation, error classification, pool timeout behavior and operational observability. If throughput is a selection criterion, use identical Postgres hardware, schema, data, connection budgets and request mix; report p50/p95/p99, throughput, CPU, locks and pool waits. Choose SQLx by default unless a measured or workflow-specific problem favors the alternative.
2. **Hot ref versus independent refs:** race many writers against one expected ref version and verify one success per generation with explicit conflicts; separately fan out writes to many repos/refs. Measure transaction latency, lock waits, WAL, pool wait, CPU and retry rates. This identifies the per-ref queue and aggregate primary ceiling independently.
3. **Tree-shape sweep:** derive snapshots for small changes in a million-entry directory, deep trees, many changed paths, and a burst of concurrent children from one parent. Compare flat manifest and paged persistent map prototypes for bytes read/written, rows/objects touched, derivation latency, cache footprint and rebuild cost. Gate persistent-format freeze on demonstrating incremental work for a one-file update without making cold reconstruction or GC impractical.
4. **Graph/index sweep:** generate histories with long linear ancestry, broad merges, many branches and criss-cross merge bases. Measure indexed traversal versus bounded fallback, including worst-case work and index rebuild time. Add skip/reachability structures only if they improve required queries and remain rebuildable within a declared recovery window.
5. **Hot-monorepo service envelope:** replay the pilot's expected commit, review, history, diff, materialization and landing mix against one repository while independently varying API workers, derivation workers, object I/O and database limits. Include a competing same-ref landing queue with realistic CI delay. A distributed database investigation is warranted only when database metadata writes or graph-index service are the bottleneck after query, index, batching, and worker tuning, and the target workload exceeds the PostgreSQL primary's demonstrated capacity with headroom.
6. **Crash/GC matrix:** inject termination after upload, before SQL commit, after SQL commit before reply, after outbox claim, and during mark/sweep while publishing a changeset. Verify retries return the same durable result, committed references resolve, indexes rebuild, and no reachable or backup-retained object is removed. Keep deletion disabled until all cases and restore from retained backup watermarks pass.

Set absolute performance and scaling targets from the pilot workload, hardware, availability objective and measured baseline. Record accepted-to-tree-ready latency, API latency, queue lag, pool waits, lock time, WAL volume, graph work, object bytes/requests, cache hit rate and restore time. Do not infer large-monorepo capacity from a many-repository benchmark or from crate/database marketing claims.
