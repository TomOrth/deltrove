# Client and frontend stack research

> Current scope: the user selected Rust for the server after this memo. The Go CLI proposal remains; share API schemas and format test vectors across languages rather than assuming Go server/client library reuse. See the [updated technical plan](../technical-plan.md).

Research checked 16 October 2026. This is a planning memo for an online-first, Scion-inspired source-control product. It describes current source facts separately from recommendations. It does not assume Git protocol or tool compatibility.

## Recommendation

For a small team building its own authoritative server and object model, start with a **Go CLI**, an in-process local cache behind an interface that could later move into an optional shared node daemon, and a **React + TypeScript + Vite SPA** for the authenticated web review client. Persist cache metadata in SQLite and immutable blobs in a content-addressed directory. Keep the CLI/cache as the only component that mutates a native working copy. Have the web UI call a versioned HTTPS API and receive event updates over SSE; it should render server-produced patches and fetch file contents on demand. If the browser later needs a local workspace, make that a separately designed capability with a local daemon pairing/security protocol, rather than having a hosted page silently reach into localhost.

This recommendation is about small-team iteration and implementation simplicity, not a claim that Go is inherently safer or faster. Choose Rust if the team already has Rust expertise, wants to embed a Rust Git implementation such as gitoxide, or considers compile-time memory/concurrency guarantees a primary risk reducer. Either language still needs explicit, cross-platform filesystem transaction and recovery design.

## Client and daemon language

**Source facts.** Rust's ownership/type system provides compile-time memory-safety guarantees without a garbage collector; the Rust book also emphasizes that ownership and type checking help manage concurrency problems ([Rust Book](https://doc.rust-lang.org/book/ch04-00-understanding-ownership.html)). Go provides a stable source-level compatibility promise for the Go 1 language and standard library ([Go 1 compatibility](https://go.dev/doc/go1compat)); its maintained first-class ports include macOS, Windows, and Linux targets ([Go porting policy](https://go.dev/wiki/PortingPolicy)). This is a meaningful distribution baseline, not proof that any filesystem behavior is identical across those OSes.

**Recommendation.** Go is the pragmatic default for this team if the product is a new online-first protocol rather than a Git implementation: its standard library makes a compact CLI/daemon, HTTP client/server, concurrency, and cross-compiling workflow straightforward. Rust is a strong alternative for a systems-heavy client with careful ownership boundaries and native filesystem code; it has a steeper onboarding/debugging cost for a small mixed-experience team. Do not choose Rust on the assumption its type system makes checkout transactions automatically safe; transaction semantics, crash recovery, and TOCTOU races remain design responsibilities.

If Git data compatibility becomes a requirement, evaluate implementations independently of language. gitoxide describes itself as an idiomatic pure Rust Git implementation and is dual MIT/Apache-2.0 ([repository and license](https://github.com/GitoxideLabs/gitoxide)); its own shortcomings document should be treated as a feature-matrix to check before relying on it. libgit2 is GPL-2.0 with a linking exception, which permits linking into other programs but has additional obligations if libgit2 itself is modified and redistributed ([libgit2 license](https://github.com/libgit2/libgit2#license), [license text](https://github.com/libgit2/libgit2/blob/main/COPYING)). That is a license-review consideration, not a reason to assume incompatibility. Preserve third-party notices and review transitive dependency licenses before shipping.

## Sparse working copy and local state

**Source facts.** Git's sparse checkout controls which paths materialize in the working tree, and Git's own documentation describes sparse checkout as one building block for a VFS-like system. Partial clone can omit objects and demand-fetch later, so commands that touch unavailable objects can require connectivity or fail; Git specifically calls out sparse merges as one case that may need data outside the selected paths ([sparse-checkout](https://git-scm.com/docs/sparse-checkout), [partial clone](https://git-scm.com/docs/partial-clone)). Therefore, Git sparse checkout is not itself a complete virtualization/placeholder filesystem, and a sparse view does not guarantee all history or operations are offline-capable.

**Recommendation: model intent and state explicitly.** Keep separate records for the committed base tree, selected/materialized path set, and observed working-copy state. `status` should enumerate the union of tracked/materialized paths and filesystem changes, with a known-path index and watcher hints backed by periodic reconciliation scans. A path outside the sparse selection is **absent by design**, not deleted. A tracked, selected path that used to exist and is now absent is a deletion. An untracked path is discovered under included directories. A path that is intentionally de-materialized during a scope change must be recorded before removal so it cannot be confused with a user deletion. Never infer deletion solely from a missing filesystem entry.

Checkout/scope changes should use a prepare/apply/commit journal:

1. Resolve the target tree and calculate the exact file actions without modifying the tree.
2. Compare each affected path against the recorded base and current file identity/content. If the user has dirty edits or a path is ambiguous, preserve it and report a conflict; do not overwrite it.
3. Persist a journal containing transaction ID, base revision, old/new scope, and per-path operation before applying writes. Write temporary files beside their destination, flush as required, then replace atomically where the platform allows. On restart, replay or roll back journaled work and verify actual file hashes.
4. Update the materialization manifest only after filesystem operations succeed. Keep object/cache writes immutable and safe to retry.

This protects the two critical cases: switching scope does not erase dirty files, and an absent sparse path does not become a delete in the next commit. `status` and `diff` should work offline for the selected files already materialized and cached. `commit` should require a live server and freeze a local snapshot consisting of the workspace's explicit parent changeset plus selected working-file contents. The server validates the supplied parent and file operations, then creates an immutable authoritative changeset; the parent may predate the current main tip. Use a request ID to make retries after uncertain timeouts idempotent. Once frozen, subsequent filesystem edits belong to the next dirty workspace snapshot and must not leak into the in-flight commit. If disconnected, retain working files and local recovery metadata; defer queued offline commits in the MVP.

For merges, have the server return a merge plan plus the necessary base/ours/theirs blobs. Apply clean merges through the same journal. For conflicts, preserve all three inputs or persist equivalent conflict metadata, leave user's working file untouched until a resolution is written, and expose explicit resolve/abort commands. A simple text merge is not a binary merge solution; report binary/large-file conflicts as unresolved. A scope-aware merge must explicitly signal unresolved out-of-scope conflicts, never silently treat unavailable paths as unchanged.

**Persistent cache.** Store small metadata locally in SQLite: repo identity, synced revision, selected scopes, materialization manifest, and journal/recovery state. Store content-addressed blobs in a separate directory with atomic write-to-temp/rename and hash verification. Treat cache contents as disposable replicas of server authority; working files and transaction recovery data must survive disconnection and process restart. SQLite WAL supports readers alongside a writer and is often faster, but WAL requires processes to share a host and does not work on network filesystems; keep the database on a local disk. In the MVP one CLI process owns the cache at a time; if later extracting it into a shared node daemon, keep the persistence and workspace interfaces stable and serialize mutations there ([SQLite WAL](https://www.sqlite.org/wal.html)). Do not copy only the main SQLite database file while active; WAL state is part of the persistent database state.

**Filesystem portability and virtualization.** Rust `std::fs::rename` documents platform-specific behavior and rejects cross-mount moves ([Rust rename](https://doc.rust-lang.org/std/fs/fn.rename.html)). Go documents that rename is not atomic on non-Unix platforms even within one directory ([Go os.Rename](https://go.dev/pkg/os/?m=all%2Cold#Rename)). Consequently, use same-directory temp writes and replacement, but do not promise crash-atomic replacement uniformly; journal and recovery are required. Add tests for case-insensitive collisions, Unicode normalization, symlinks/reparse points, read-only files, permissions, path separators, long paths, locked/open files, watcher event loss/coalescing, and interrupted writes. Keep paths as validated repository-relative logical paths and reject traversal, absolute paths, and aliases outside the workspace. Define whether names are Unicode-only, since host filesystems differ in what names they can represent.

Do not build a true virtual filesystem for the MVP. On-demand hydration requires OS-specific providers, placeholder metadata, callbacks, file pinning, offline behavior, and reliable interaction with editors/build tools. Ship explicit materialized directories first. If later needed, build an OS adapter behind a platform-neutral hydration API and test the actual OS provider; do not claim sparse directories behave as if every file exists. Git's sparse-checkout documentation discusses this distinction directly ([Git sparse-checkout](https://git-scm.com/docs/sparse-checkout)).

## Web frontend and review experience

**Framework facts.** React is a UI library built from composable components ([React docs](https://react.dev/learn/describing-the-ui)). Vite provides an ESM-based development server and bundles production assets ([Vite guide](https://vite.dev/guide/)). Next.js provides an application framework with server/client rendering and a Node.js server deployment path ([Next.js self-hosting](https://nextjs.org/docs/app/guides/self-hosting)). SvelteKit provides routing, SSR/client rendering, offline support, and static output options ([SvelteKit introduction](https://svelte.dev/docs/kit/introduction)).

**Recommendation.** Use React + Vite for this product's first web client: it is a client-heavy review UI whose data and permissions belong in an API, with no current SEO or server-rendered public content requirement. Vite yields a static artifact that can be served from a CDN or same-origin API gateway. Next.js would add value if public review pages, server-rendered sharing links, or server-side web flows become central; SvelteKit is a good option if the team already prefers Svelte, but switching frameworks does not solve the API or diff-performance design. Keep API client/types generated from an OpenAPI schema so CLI, UI, and server contracts remain explicit.

**API and transport.** Define a versioned JSON/HTTP API with stable resource IDs and idempotency keys: repositories, workspaces, revisions, changesets, file/tree reads, commit creation, merge preview, conflict resolution, and job status. Use ordinary HTTP for request/response work and Server-Sent Events for server-to-browser notifications (sync progress, review updates, merge-job completion), with reconnect cursors and polling fallback. Return structured errors and explicit states such as `missing_due_to_scope`, `needs_fetch`, and `conflict`; never overload an empty file body or 404 to mean both absent and intentionally sparse. Large blobs should be streamed/ranged and fetched only when opened. The protocol is a proposed product API; it does not promise Git smart-HTTP, Git remote-helper, or compatibility with existing Git clients/tools.

For an authenticated hosted app, keep browser traffic same-origin behind the web/API gateway, use the organization's OIDC/OAuth provider, secure and rotate server sessions, and enforce repository authorization on every endpoint. If later the browser must call a user's local daemon, treat that as a separate security boundary: bind only to loopback, require an explicit pairing step and short-lived per-origin capability, validate `Origin`/Host and CSRF protections, avoid wildcard CORS, and expose only a narrow allowlist API. Browser local-network/loopback access now has secure-context and permission constraints in some browser contexts ([MDN local network access](https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/Local_network_access)); the same-origin model keys on scheme, host, and port, with CORS controlling selected cross-origin access ([MDN Origin](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Origin)). Do not embed a shared secret in a distributed client. For native OAuth login, RFC 8252 recommends an external user agent, loopback IP redirect support, and PKCE for public clients ([RFC 8252](https://www.rfc-editor.org/rfc/rfc8252/)).

**Diff/code review.** Monaco is the browser editor component underlying VS Code's editor and has a built-in diff editor; its project license is MIT ([Monaco API](https://microsoft.github.io/monaco-editor/typedoc/interfaces/editor_editor_api.editor.IDiffEditorOptions.html), [license](https://github.com/microsoft/monaco-editor/blob/main/LICENSE.txt)). CodeMirror 6 has a merge package and is MIT-licensed ([merge package](https://codemirror.net/docs/ref/#merge), [repository license](https://github.com/codemirror/dev/blob/main/LICENSE)). VS Code documents inline/side-by-side diffs, collapsing unchanged regions for large files, and a unified accessible diff viewer ([diff and staging guide](https://code.visualstudio.com/docs/sourcecontrol/staging-commits), [accessibility guide](https://code.visualstudio.com/docs/configure/accessibility/accessibility)).

For a code-review app, start with a lightweight unified patch renderer for list/overview and use Monaco's diff editor only for an opened file, with a plain unified-text mode available for assistive technology and constrained devices. Monaco has a richer editor surface and language features but increases initial payload and worker/configuration cost; CodeMirror is modular and smaller, but its merge package is for editor-side comparison and does not replace the backend merge algorithm. Keep server-generated diff hunks as the review source of truth. Paginate change lists, lazy-load per-file diff data, collapse context, virtualize long file lists, cap rendered line counts, and provide a download/raw view for enormous or binary changes. Never parse or diff every repository blob in the browser. Aim for keyboard operation, visible focus, semantic labels, high contrast, and screen-reader announcements. The W3C ARIA APG describes the keyboard behavior authors must provide for custom widgets ([WAI-ARIA APG](https://www.w3.org/WAI/ARIA/apg/)); do not assume a code editor makes the surrounding review UI accessible.

## Concrete MVP workflows

1. `oscn auth login` opens the system browser for OAuth/PKCE, stores a refresh credential in the OS keychain where available, and reports the selected account/server.
2. `oscn clone <repo> --include src/service` creates a local metadata cache, fetches only the selected tree/files, writes a materialization manifest, and prints exactly what was downloaded and omitted.
3. `oscn status` lists modified, added, deleted, untracked, and conflicted files; it labels skipped paths as outside scope and never lists them as deletions.
4. `oscn scope add/remove` previews paths that will materialize or be removed. It refuses to drop dirty files unless the user saves/commits or chooses an explicit preservation action. It can run offline only when the required tree/blob data is cached.
5. `oscn diff [path]` shows base-to-working changes, including offline edits to materialized files. `oscn commit -m ...` requires a live server and creates an immutable changeset whose parent is the workspace's explicit base, even when that base is behind main. It freezes the selected working-file snapshot before upload; edits made during upload remain dirty for a later commit. A request ID makes retry after a timeout idempotent; failed requests leave working files intact.
6. `oscn sync` fetches the current head and newly needed selected files, then reconciles the user's offline edits. It either fast-forwards clean files while preserving local edits or writes conflict metadata without discarding user content. `oscn resolve` records a chosen resolution; `oscn merge abort` returns to the pre-merge snapshot. Offline editing/status/diff are MVP features; offline commit queueing is deferred.
7. Web review lists changes, lazily loads hunks, supports inline/side-by-side view, comments, keyboard navigation, and an accessible unified patch view. It does not need access to a developer's local files.

## Meaningful early checks

Build table-driven workspace integration tests that create a fixture repository and exercise: (a) sparse omission remains absent in status/commit; (b) deleting a materialized tracked file is detected; (c) scope removal refuses to discard dirty content; (d) a crash injected after each journaled checkout step recovers without data loss; (e) a merge with clean, text-conflicting, binary, and out-of-scope changes produces explicit outcomes; (f) retries after server timeout are idempotent; and (g) path traversal, symlink escape, case-fold collision, and Unicode-name edge cases are rejected or handled by the documented policy. Run the suite on macOS, Windows, and Linux because rename, permissions, symlinks, locks, and watcher behavior differ. For the UI, automate keyboard-only navigation and screen-reader-relevant semantics on the review flow, and profile a fixture with thousands of changed files plus one very large patch to verify lazy loading and bounded rendering. These checks target failure modes that a happy-path unit test will miss.
