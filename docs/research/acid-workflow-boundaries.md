# ACID and durable workflow boundaries

> Synthesis update: the [adopted durability plan](../durability-and-workflows.md) deliberately tightens the initial critical-mutation isolation default to `SERIALIZABLE`. This memo's discussion of when explicit locks/CAS can support `READ COMMITTED` remains an analysis of a possible reviewed optimization, not the current default.

**Date:** 16 October 2026. **Status:** architecture review; no implementation or failure tests run. Supplements `technical-plan.md` and `rust-backend-scaling.md`.

## Decision

Keep PostgreSQL as authority for mutable source-control metadata and begin with its transactional outbox/job queue plus fenced Rust workers. This is sufficient for the MVP with bounded retryable jobs, short SQL transactions, one metadata write primary, and no long human/CI wait represented as an in-memory task. Add Temporal when workflows span long waits, need operator-visible histories/signals/versioned orchestration, or require complex recovery across services. Its Rust SDK is documented, so a second-language worker is unnecessary. DBOS has an official MIT-licensed Rust SDK, but it is early and currently lacks transactional steps, so instrumented writes are at-least-once rather than transactionally exactly-once. Restate's Rust SDK is MIT, but the Restate server is under BSL 1.1 rather than an open-source license; exclude it from the open-source shortlist unless that licensing constraint changes.

An orchestrator is not the correctness boundary for refs, reviews, checks, or policies. Preserve the final PostgreSQL transaction and use workflow software to arrange/retry surrounding steps. No engine makes PostgreSQL and object storage atomic together or guarantees exactly-once effects at arbitrary CI endpoints.

## Invariants and transaction boundaries

| Invariant | Atomic boundary / required mechanism | Isolation and retry guidance |
| --- | --- | --- |
| An acknowledged immutable object is addressable by its digest and not partially visible | Stream to a unique immutable key; verify length and digest; wait for successful durable store completion; then commit object metadata, membership/pin and idempotency outcome in PostgreSQL. Never publish DB reachability before storage success. | Object PUT is outside SQL. Retry idempotent writes to the same content-addressed key. Use conditional create/version checks where provider supports them; never permit key reuse with different bytes. |
| A changeset request returns one stable result after timeout/retry | In one SQL transaction, insert/reconcile `(repo, actor, idempotency_key, request_hash)`, immutable changeset metadata/parents/path ops, object references/pins, derivation job/outbox row, and response outcome. Same key + same request returns stored result; same key + different request is rejected. | `READ COMMITTED` is adequate with unique constraints and explicit row locks/CAS for these keyed invariants. Keep large uploads and derivation outside the transaction. |
| Derivation cannot publish stale or incomplete snapshots | Worker reads pinned immutable inputs, writes immutable derived objects, then transactionally checks job attempt/fencing token and expected derivation state before marking ready and linking the exact root. | Claim with `SKIP LOCKED` in a short transaction; lease expiry is not cancellation. Token-check every completion. Duplicate object writes are safe; stale SQL publication is not. |
| A landing is authorized for exactly the reviewed candidate and target generation | One final SQL transaction validates target ID+generation, candidate ID/readiness, review revision, approvals, required checks and producer identity, current permissions/policy generation, then advances ref, records landing/audit/idempotency outcome, and inserts outbox notifications. | Prefer explicit version/generation rows, unique constraints and a fixed lock order. `READ COMMITTED` plus those locks/CAS can suffice if every relevant mutation bumps its generation and conflicts are serialized. Use `SERIALIZABLE` if a business invariant depends on a predicate/set of rows not covered by a stable lock/version; retry the *whole* transaction on SQLSTATE `40001` and deadlocks. `REPEATABLE READ` alone can still permit write skew. |
| A check result applies only to its exact immutable candidate and authenticated producer | A short SQL transaction validates scoped credential/producer, candidate/revision identity, allowed state transition and callback idempotency key; stores result and advances check generation. The landing transaction rechecks that generation and current requirements. | `READ COMMITTED` plus row locks/unique constraints is suitable for state-machine transitions. Revoke/permission changes participate in the shared policy generation/locking protocol. |
| A committed mutation eventually emits downstream work | Write outbox row in the same SQL transaction as its authoritative mutation. Dispatcher claims/leases and sends at least once; consumers deduplicate by stable event ID. | Never publish before commit; never hold SQL transaction open for broker/network calls. Delivery is at least once. |

The transaction must not include S3 calls, blob uploads, CI execution, merge computation, or workflow waits. The immutable candidate must be built and checked before the final short landing transaction; that transaction verifies the inputs remain current. PostgreSQL documents that its `REPEATABLE READ` snapshot isolation can admit serialization anomalies, while `SERIALIZABLE` detects dangerous read/write patterns and aborts one participant; the application must retry the full transaction ([isolation](https://www.postgresql.org/docs/current/transaction-iso.html), [application consistency](https://www.postgresql.org/docs/current/applevel-consistency.html)).

## Cross-store publication protocol

PostgreSQL and S3-compatible storage have no shared commit. Use an **objects-first, metadata-second** protocol: reserve upload/idempotency state and quota in SQL; stream to a fresh immutable key; verify raw digest/length; wait for storage acknowledgement; then atomically commit object metadata/pins, changeset publication, job/outbox and idempotency response in SQL. If storage succeeds and SQL fails, leave an unreferenced immutable object for later conservative cleanup. If SQL commits, required bytes must already exist and be protected from GC. Never delete the orphan immediately: a lost response or retry could still be reconciling it.

For AWS S3, successful PUTs have strong read-after-write consistency and an individual key update is atomic, but updates across keys are not atomic and concurrent same-key PUTs need application coordination ([S3 consistency](https://docs.aws.amazon.com/AmazonS3/latest/userguide/Welcome.html)). Do not generalize those guarantees to every “S3-compatible” store; qualify each adapter, including durability, conditional requests, multipart completion/abort, versioning and failure behavior. The source-control correctness property is a protocol plus provider contract, not an S3 label.

## Durability, replication and recovery

An acknowledged SQL commit is only as durable as the deployed PostgreSQL settings and storage stack. Keep `fsync=on` and synchronous commit for acknowledged mutations; do not weaken them to meet latency targets without changing the durability contract. Local WAL flush protects against process/OS crash under trustworthy storage semantics. It does not protect against loss of the primary volume or site. PostgreSQL streaming replication is asynchronous by default, so failover can lose transactions already acknowledged by the primary. Synchronous replication can wait for remote WAL flush; `remote_apply` additionally waits for replay/visibility and adds latency ([WAL settings](https://www.postgresql.org/docs/current/runtime-config-wal.html), [replication](https://www.postgresql.org/docs/current/warm-standby.html)). Observed replication lag is not a hard RPO bound: only a failover policy that prevents promotion beyond a defined durable position can enforce one. State the chosen RPO against actual replication mode and failover policy, not merely “Postgres HA.”

PITR is a different control: a base backup plus a continuous, gap-free WAL archive permits restoring a cluster to a chosen point in time. It is not synchronous failover and does not by itself preserve object-store bytes. Pair each advertised DB recovery window with retained object roots plus all objects published after the backup watermark; restore DB and objects together, then scrub reachable objects before reopening writes. Rehearse restore into an empty environment and record measured RPO/RTO. PostgreSQL's [PITR guide](https://www.postgresql.org/docs/current/continuous-archiving.html) describes the WAL/base-backup mechanism and the need for a continuous archive.

## Failure matrix

| Failure point | Required state/result | Recovery behavior |
| --- | --- | --- |
| Upload interrupted before verification | No published changeset; reservation can expire; partial multipart upload is aborted eventually | Client resumes/restarts with same operation identity; partial bytes never become reachable. |
| Object PUT succeeds; SQL publication fails | Orphan immutable object, no visible changeset | Retry SQL publication idempotently or retain for delayed GC; scrubber finds unreferenced data. |
| SQL publication commits; HTTP response is lost | Published changeset and durable outcome exist | Retry/reconcile by idempotency key returns same result; no second logical changeset. |
| Worker dies after work, before SQL completion | Job remains reclaimable; immutable outputs may be duplicated | New attempt recomputes or validates outputs; old fencing token cannot publish. |
| Lease expires while old worker is paused | Two workers may run; one current attempt is authoritative | Monotonic fencing token checked on every SQL completion/ref write; lease alone is insufficient. |
| CI accepts request but callback/response is lost | Runner may have executed candidate; status is uncertain | Re-dispatch with stable check/execution idempotency key where provider supports it; callback dedupe; reconcile runner status. External execution may occur more than once. |
| Candidate/check/policy changes during landing | Landing must not use stale approval/check/policy | Final transaction sees generation mismatch and aborts/requeues revalidation. |
| Async DB failover loses recent WAL | Acknowledged metadata since the promoted replica's durable position may be lost | Measured lag is not a hard RPO unless the promotion policy enforces that bound; coordinate object retention and operation reconciliation after failover. |
| PITR restores DB behind object store | Newer objects are unreachable orphans; restored refs cannot point to absent bytes | Keep objects through recovery window; restore at recorded watermark, scrub before writes; never run normal GC during reconciliation. |
| Outbox consumer is down or duplicates delivery | Domain transaction remains committed; notification delayed/duplicated | Retry delivery and dedupe by event ID; expose backlog/age. |

## Orchestrator choice

**PostgreSQL jobs are enough for the MVP** because the current scope has bounded derivation jobs and one landing state machine, while PostgreSQL is already the metadata authority. A transactional outbox removes the dual-write gap between domain commit and job enqueue. Worker leases, attempt tokens, durable state transitions, retry limits, queue classes and idempotent operations provide crash recovery without another cluster. This is a deliberate correctness design, not a shortcut around one: test process kills, lease takeover, response loss, duplicate delivery, database restart and object-store errors.

Adopt **Temporal** when the workflow itself becomes a product-scale concern: approvals/CI can wait for hours or days, workflows need signals/cancellation/operator intervention, many step types need independent retry/backoff/timeouts, or replayable histories materially improve incident recovery. Temporal records workflow event history and reconstructs execution after worker failure. An Activity Execution can involve several Activity Task Executions, so external effects need idempotency or deduplication ([event history](https://docs.temporal.io/encyclopedia/event-history), [Activity task semantics](https://docs.temporal.io/tasks)). The official docs list a Rust SDK ([SDKs](https://docs.temporal.io/develop)). A Temporal workflow may orchestrate “build candidate → request CI → wait for callback → attempt landing,” but the last PostgreSQL transaction remains authoritative. Temporal workflow state and PostgreSQL state are not one ACID transaction; use a durable start/outbox handshake and idempotent workflow ID. Preserve the outbox or an equivalent atomic handoff.

**DBOS** is attractive when same-database workflow durability and transactional SQL integration are desired. It provides an official MIT-licensed Rust crate/repository, backed by PostgreSQL, but its current Rust implementation explicitly has no transactional step; its example writes can repeat at least once after recovery ([Rust DBOS repository](https://github.com/dbos-inc/dbos-transact-rust)). Treat it as an early durable-workflow library, not a drop-in for transactional guarantees documented for other DBOS SDKs. Reevaluate when Rust transactional steps are implemented and version maturity is acceptable. It still cannot make arbitrary HTTP/CI effects exactly once.

Restate is excluded from consideration for this open-source project: although its Rust SDK is MIT, the server uses BSL 1.1, which its own license identifies as not open source ([server license](https://github.com/restatedev/restate/blob/main/LICENSE)).

## Unresolved choices to close before production

1. Define acknowledged-commit durability: local WAL only or synchronous replica, acceptable failover RPO, WAL archive target/retention, and restore RTO.
2. Choose the idempotency-key retention period and semantics for same key/different payload; define object reservation and orphan retention/GC windows.
3. Specify per S3-compatible provider whether conditional immutable creation, multipart recovery, versioning and acknowledged durability meet the protocol.
4. Lock in a concrete landing schema/generation protocol and decide which policy predicates need serializable isolation versus explicit row locks/CAS. Document global lock order and retry classification.
5. Define check-runner idempotency and reconciliation capabilities; where the provider cannot deduplicate, explicitly accept duplicate execution and bind each result to the exact candidate and run identity.
6. Revisit Temporal or DBOS after measuring workflow duration, operator burden, queue age and retry complexity; if adopted, keep payloads as IDs/object references and retain DB-owned landing authority.

No compliance or certification claim follows from these design choices. All durability and execution guarantees must be tied to deployed configuration, provider contracts and rehearsed failure/restore evidence.
