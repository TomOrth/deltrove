# Prior art for an open-source Scion-inspired source control tool

**Research date:** 2026-10-16. Public-source status and license notes below were checked on this date; repository `main` pages can change. This is a design memo, not a claim about this repository's implementation and not legal advice.

## Recommendation

Keep interoperability as the first product constraint. Start by proving a useful workflow on ordinary Git repositories, using Git's partial-clone and sparse-checkout machinery where it fits. Treat Jujutsu as a candidate for Git-native client semantics and an adoption bridge, not as an already-built server-first monorepo backend. Use Sapling/Mononoke and Google's Piper/CitC as design references; do not plan on adopting their full stacks as supported, drop-in open-source products. If the intended product truly needs a central, always-online service, define a narrow server API and immutable content model behind a Git import/export boundary, then validate with real workloads before replacing Git storage or workflows.

This staged recommendation is a proposed design judgment. No performance claim follows from the prior-art systems.

## Reuse versus build

**Reuse now:** Git object formats, protocol, partial clone, sparse checkout, Git worktrees, and established Git hosts give the broadest interoperability. Jujutsu can be evaluated as a client experience over Git; avoid making its working-copy/operation-log model an assumed server architecture. Sapling provides a broad CLI and examples for sparse profiles and stack workflow, but is GPL-2.0 at the project level and its scalable server and VFS are explicitly unsupported for external production use.

**Borrow as patterns:** From Mononoke, separate protocol-facing services from canonical internal representation; distinguish immutable content from mutable refs; move expensive indexes/representations off the critical write path only when readers can tolerate and detect lag. Prototype API-first operations and object-fetch strategies against the target workload before adding repository mirrors or a virtual filesystem. Treat filesystem virtualization as a separate subsystem with its own consistency and operational requirements.

**Build only when demanded:** A new server authority, APIs for ancestry/diff/blame, ACL and audit model, indexing pipeline, cache tier, or virtual filesystem should each be justified by a measured workload and migration plan. A central server changes the failure model: authoritative commits and requests for uncached history or objects need service access, while edits to already materialized files can continue locally. If inventing a storage model, write down merge-parent semantics, rename/copy tracking, paths, symlinks, submodules, LFS, refs, signatures, and recovery semantics before migration.

## Migration and compatibility lessons

1. **Define the compatibility boundary, then migrate consumers in slices.** Preserve a Git import/export or gateway path while clients, CI, review, search, and automation move; “Git-compatible commits” alone will not preserve the surrounding workflow.
2. **Treat Git as behavior, not just object encoding.** Existing tools read the index, refs, reflogs, config, hooks, attributes, submodules, LFS pointers, signatures, merge state, and branch/HEAD conventions. Sapling and Jujutsu documents enumerate concrete mismatches even when the underlying `.git` directory remains usable.
3. **Partial data makes commands network-dependent.** Git partial clones may fetch blobs as a side effect of diffs, merges, history, or blame. Pin and report the remote needed to hydrate data; define offline behavior and prefetch rules. Sparse working trees and sparse object stores are separate features.
4. **Don't equate “lock-free” with no coordination.** Mononoke has a dedicated landing service that serializes public bookmark movement; Jujutsu detects concurrent repository-state operations, while its Git backend still has locking/corruption limitations. Be explicit about which operations are immutable writes, per-ref compare-and-swap, serialized landing, or conflict-producing concurrent updates.
5. **Migration fidelity needs explicit evidence.** Specify round-trip invariants for object IDs, signatures, notes, tags, merge parents, and rollback before cutover; validate them against representative repositories. Do not infer system migration guarantees from high-level case studies.
6. **Authorization must be enforced through derived data and caches.** For a central service, access checks should cover directory listings, histories, blame, search, errors, and cached blobs/indexes; a sparse checkout is not an access-control boundary. This is a design recommendation, not a claim about any compared system's policy implementation.

## Uncertainties and caveats

- Meta's current GitHub `main` source is public but explicitly not externally supported for Mononoke/EdenFS. OSS buildability is not the same as an operable production service.
- Google's primary publication record is accessible, but the full text was not; details of CitC's architecture remain unverified in this memo.
- License labels are repository-level starting points, not a complete software bill of materials. Check notices, generated code, bundled dependencies, and each subdirectory before copying code.
- Performance figures published by the organizations describe their own systems and workloads. No figure should be used as a Deltrove target without a benchmark using the actual repository shape, client mix, network, and CI access patterns.
