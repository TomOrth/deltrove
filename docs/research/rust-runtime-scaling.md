# Rust server runtime and scaling research

**Date:** 16 October 2026\
**Scope:** Rust server execution, transport, admission, CPU isolation, streaming, cache behavior, and operational measurement for Open Scion. This assumes the user has selected Rust for the server. It makes no recommendation to change the separately selected CLI language. This is a research memo, not measured capacity guidance.

## Recommendation

Use Tokio + Axum + Tower for the first Rust server, with one documented HTTP/OpenAPI API and streaming binary object endpoints. Keep handlers mostly asynchronous, use shared explicit admission controls, and run diff/merge/graph CPU work through a separately sized Rayon pool or dedicated worker process. Use Tokio `spawn_blocking` for short, bounded blocking calls only. Keep the object cache process-local and small initially; Moka is a good metadata/small-object cache, while large blob bodies need a byte-budgeted cache policy. For S3 I/O, preserve streaming across the HTTP body and object-store boundary, with bounded buffers and upload concurrency.

These defaults are hypotheses for a first deployment, not claims about throughput. Start with one process on a modest 8-vCPU / 16-GiB host as a reproducible benchmark target; derive every limit from load tests and the service's latency and memory targets. No Kubernetes dependency is implied: a single binary/image and Compose deployment can use the same pools and limits.

## Runtime and HTTP stack

Tokio's multi-thread runtime is a sound baseline for network and database I/O. Axum's body API can wrap streams directly, and `utoipa` with `utoipa-axum` can produce an OpenAPI document alongside route registration. Keep API/domain types separate from Axum extractors and response types so transport changes remain possible. [Tokio runtime and blocking task docs](https://docs.rs/tokio/latest/tokio/task/fn.spawn_blocking.html), [Axum `Body`](https://docs.rs/axum/latest/axum/body/struct.Body.html), [Utoipa Axum integration](https://docs.rs/utoipa-axum/latest/utoipa_axum/).

Use HTTPS JSON/OpenAPI for metadata and ordinary operations, and distinct `application/octet-stream` endpoints for uploads/downloads. A browser and CLI can then use the same API without imposing Protobuf generation, gRPC-Web handling, or a proxy requirement on the initial deployment. This aligns with the technical plan's one-contract direction. SSE is sufficient for low-volume operation/review updates; it should not carry object data. If a later internal service boundary has a measured need for typed RPC or bidirectional streams, evaluate Tonic separately while keeping HTTP as the browser/integration contract.

Tonic-Web is a Tonic server adapter that accepts gRPC-Web requests, but the browser protocol has different capability constraints from native gRPC. The grpc-web project's own README says server streaming is available only in `grpcwebtext` mode; client and bidirectional streaming are not listed as supported. That makes gRPC-Web a poor default for large binary object transfer or interactive duplex traffic. A native CLI may use generated gRPC clients if an internal protocol later justifies it, but duplicating public REST and RPC contracts in the MVP would increase compatibility work. [Tonic-Web README](https://github.com/grpc/grpc-rust/blob/master/tonic-web/README.md), [gRPC-Web support matrix](https://github.com/grpc/grpc-web/blob/master/README.md).

Axum/Tower middleware is useful for route-scoped timeouts and concurrency limits, with an important streaming caveat: Tower's concurrency permit is stored in the response future and is released when that future produces the `Response` headers. The response body's later streaming lifetime is outside that future, so the layer alone does not cap active downloads or SSE streams. Acquire a dedicated stream permit in the handler and move it into a wrapper around the response body so it is held until end-of-stream or client disconnect; meter bytes separately. [Tower concurrency response future source](https://docs.rs/tower/latest/src/tower/limit/concurrency/future.rs.html). Tower's `GlobalConcurrencyLimitLayer` shares one semaphore across services, which is the important distinction from a separately layered per-route limit. A concurrency limit alone can still leave callers waiting in memory; combine it with bounded request/body limits and either an explicit short queue deadline or immediate overload response. [Tower concurrency layer source](https://docs.rs/tower/latest/src/tower/limit/concurrency/layer.rs.html). `tower-http` distinguishes whole-handler timeout from request/response body idle timeout and absolute body deadline, allowing slow clients to be bounded without applying an unsuitable short total deadline to a large upload. [tower-http timeout docs](https://docs.rs/tower-http/latest/tower_http/timeout/index.html).

## Admission, concurrency, and memory budgets

Use separate controls for distinct constrained resources:

| Resource | Initial tunable hypothesis | Rationale and caveat |
| --- | --- | --- |
| Tokio async workers | Tokio default based on available parallelism | Async workers should handle readiness and I/O, not long CPU loops. Alter only after runtime metrics show worker saturation or excess context switching. |
| General request admission | Shared semaphore: 256 active requests/process; per-route tighter caps for expensive endpoints | A modest initial guardrail for retained per-request state, not a universal capacity. Use a try-acquire or bounded wait and return 503/429 with retry guidance under overload. Include health/readiness in a small reserved lane. |
| Diff/merge/graph CPU | Rayon pool `min(4, max(1, cores/2))` on an 8-vCPU starter; one permit per admitted task, with smaller weighted limits for memory-heavy work | Preserves CPU for async runtime, DB, storage and OS. CPU work that scales poorly should not occupy every core. Increase only from representative profile results. |
| `spawn_blocking` | No CPU algorithms here. If needed, inventory calls first; set a finite Tokio blocking-thread ceiling (initial 32–64) only if application code uses it materially | Tokio's default ceiling is 512 and its blocking pool also serves runtime operations such as filesystem/DNS; an arbitrarily tiny ceiling can stall those operations. Started blocking work cannot be cancelled. |
| Object upload body | 256-KiB frames, at most 16 in-flight uploads/process, and a small bounded number of frames in flight per upload (e.g. 4) | Approximately 16 MiB of application frame payload at this hypothesis, before SDK/HTTP/TLS buffers and metadata. Derive a real memory budget from measured copy behavior. |
| Download body | Stream one bounded chunk at a time; cap active streams separately (initial 64/process), with a shared retained-byte budget | Backpressure should flow from a slow client toward storage reads; do not prefetch whole objects or fan out unlimited chunks. Hold the stream permit through body completion/disconnect, not just until headers are sent. Lower the cap where each stream retains significant state. |
| Per-request materialization | Default cap 16 MiB for JSON/tree/graph responses; paginate larger results | Body and decoded representation may coexist. Keep binary object limits independent and explicit. |
| Cache | Start with a Moka weighted capacity around 256 MiB of estimated entry payload for metadata/small immutable objects; separately enforce a process memory target | Moka supports a custom weigher and weighted capacity. The weight estimate can guide eviction, but Moka's best-effort policy and estimate do not provide a hard RSS ceiling. |

Treat these as separately configurable limits, and expose active/queued/rejected counts, wait time, and retained-byte estimates. Tokio's semaphore is fair, so a large `acquire_many` request queued at the front can hold up smaller acquisitions. Avoid mixing large weighted acquisitions on one semaphore; use separate classes or a nonblocking admission decision when fairness would create head-of-line blocking. [Tokio Semaphore docs](https://docs.rs/tokio/latest/tokio/sync/struct.Semaphore.html).

For the self-hosted single-node MVP, one process-wide budget is enough. For large organizations, first scale horizontally by adding identical API/worker processes and partitioning jobs by repository or queue class, while preserving Postgres as the transactional authority. A semaphore is process-local; if fleet-wide limits matter (for example, S3 request ceilings or a per-tenant CPU quota), enforce them at a shared queue, database lease, gateway, or storage provider boundary. Do not mistake a local limit for an organization-wide limit. Keep a reserved path for cheap ref/file reads so bulk imports and graph derivations cannot starve interactive review traffic.

Use independent budgets for DB pool connections, storage requests, upload bytes, and CPU jobs. Bound every queue and report overload explicitly. Tokio's guidance emphasizes that unbounded queues can consume all memory and recommends choosing explicit capacities; a bounded channel's capacity is the maximum pending element count. [Tokio backpressure and bounded-channel guidance](https://tokio.rs/tokio/tutorial/channels), [Tokio sync channel docs](https://docs.rs/tokio/latest/tokio/sync/index.html).

## CPU work, cancellation, and bounded pipelines

Diff, merge, ancestry/graph traversal, compression, hashing of large payloads, and expensive index derivations can be CPU-heavy. Do not run long loops directly inside an async handler: a future that does not yield can starve unrelated tasks on its Tokio worker. Tokio documents `spawn_blocking` as a bridge for blocking work, but its pool grows to a high ceiling, queues after that ceiling, and cannot abort a started closure. Use it for short bounded synchronous APIs; put sustained CPU workloads behind explicit admission and a dedicated Rayon pool or separately deployed worker. [Tokio `spawn_blocking` details](https://docs.rs/tokio/latest/tokio/task/fn.spawn_blocking.html), [Rayon user thread-pool docs](https://docs.rs/rayon/latest/rayon/struct.ThreadPool.html).

Rayon gives a fixed-size work-stealing pool with an explicit `ThreadPoolBuilder`; use a project-owned pool rather than silently sharing Rayon global state with unrelated dependencies. Keep the task queue bounded before submitting work—Rayon's worker count does not by itself bound queued jobs or input data retained by those jobs. Acquire CPU and memory permits before cloning/materializing a large input, then move owned permits into the Rayon closure (or `spawn_blocking` closure) and release them only when that computation actually exits. Do not keep the only permit in the request future: if that future is cancelled while non-cancellable CPU work continues, releasing it early admits more work than the configured CPU/memory budget. For CPU jobs that do not finish promptly, use cooperative cancellation flags and poll them inside the algorithm; a dropped join handle does not stop already-running work. A separate worker process is the next isolation step when CPU jobs need independent restart, autoscaling, or memory ceilings; it need not require Kubernetes and can initially be another Compose service or systemd unit. [Rayon `ThreadPoolBuilder`](https://docs.rs/rayon/latest/rayon/struct.ThreadPoolBuilder.html), [Tokio `spawn_blocking` cancellation behavior](https://docs.rs/tokio/latest/tokio/task/fn.spawn_blocking.html).

Cancellation needs explicit semantics. A timeout layer can cancel its wrapped handler future, and transport stacks can report failed writes or dropped bodies, but do not assume every client socket disconnect immediately or universally cancels application work. Explicitly observe body/write errors and pass a cancellation token/atomic flag into long CPU loops; check it at bounded intervals and test disconnect behavior through the deployed HTTP/proxy path. Cancellation does not preempt a Rayon closure or a started `spawn_blocking` closure. Ensure cancellation drops temporary output and does not publish partial objects or metadata. At durable mutation boundaries, use idempotency keys and operation records so cancellation after the server commits but before the response does not invite duplicate writes. For upload, write to a temporary/reserved object key and only finalize after length/digest validation and transactional metadata handoff; cleanup must account for leases and GC roots.

Tokio documents that several I/O and permit-wait methods are not cancellation-safe when restarted inside `select!`; for example `read_exact`, `write_all`, and semaphore acquisition can lose progress or queue position. Keep cancellation at transaction boundaries or use resumable chunk protocols with offsets/idempotency, rather than restarting an opaque sequence of side effects. [Tokio cancellation-safety list](https://docs.rs/tokio/latest/tokio/macro.select.html).

Pipeline upload/download work as streams: read a frame, validate/account/hash it, write the next frame, and wait before buffering more. Any producer-consumer bridge should be a bounded `tokio::mpsc::channel`, not an unbounded queue. Avoid collecting Axum request bodies into `Bytes` for normal object sizes; reserve `to_bytes` for small, explicitly capped payloads. A stream allows backpressure only if each stage respects polling and does not spawn unbounded producers. [Axum body stream API](https://docs.rs/axum/latest/axum/body/struct.Body.html), [Tokio bounded channels](https://tokio.rs/tokio/tutorial/channels).

## Object storage streaming and backpressure

Keep the client upload stream and S3 request body streaming end-to-end where the selected SDK supports it. Do not read a whole blob into a `Vec` just to hash or upload it. Hash incrementally while streaming, enforce declared and actual size limits, and publish the digest-named immutable object only after a successful complete write and verification. For large uploads, use multipart upload with bounded part size and bounded parallelism; abort incomplete multipart uploads on failure and expire them with storage lifecycle policy as a cleanup aid, not as the authority for object reachability.

The Rust `object_store` crate exposes async object-store reads, ranges, and multipart upload support; its multipart writer is described as avoiding buffering the entire object and uploading fixed-size parts. It is a reasonable abstraction to spike for local filesystem plus S3-compatible backends. Verify each target's conditional put, multipart abort/cleanup, range behavior, and consistency semantics in an adapter suite before relying on them for immutability or GC. If a required provider feature is not expressible through the abstraction, keep a narrowly scoped provider adapter or use the provider SDK directly rather than flattening important semantics. [object_store crate overview](https://docs.rs/object_store/latest/object_store/), [object_store range API](https://docs.rs/object_store/latest/object_store/enum.GetRange.html).

The AWS Rust SDK represents S3 object bodies as `ByteStream` and supports constructing upload bodies from files; this demonstrates an SDK streaming body abstraction, but not equivalent behavior for every S3-compatible service. For each adapter, measure request buffering, multipart parallelism, retry duplication, checksum validation, and cancellation cleanup. [AWS SDK for Rust S3 examples](https://docs.aws.amazon.com/sdk-for-rust/latest/dg/rust_s3_code_examples.html).

For downloads, authorize before serving a cache hit or opening storage; stream the response body, set content length when known, and honor range requests only where the object semantics support them. When a disconnect or body-write error is observed, stop issuing future range reads and release stream permits. A bounded prefetch window (start at one chunk, optionally test two) can hide storage latency without letting a slow client accumulate unlimited memory. For uploads, cap concurrent requests and per-tenant bytes in flight, and make retries resume an explicit upload session or restart an idempotent single-object write. Axum's `DefaultBodyLimit` protects `Bytes`/`Json`-style extractors, but does not apply when a handler consumes a raw `Body` stream directly; raw streaming object routes need an explicit running byte counter and hard cap, regardless of `Content-Length`. `RequestBodyLimitLayer` is a separate global middleware option, but route semantics still need clear configured size limits. [Axum `DefaultBodyLimit` caveat](https://docs.rs/axum/latest/axum/extract/struct.DefaultBodyLimit.html). Keep the existing plan's separate finalize step so object durability and SQL publication have a clear boundary.

## Cache choice and stampede behavior

Moka's async cache is a strong first process-local cache for immutable metadata, tree pages, small blobs, and authorization-independent derived records. Its `try_get_with`/`get_with` initialization coalesces concurrent misses for the same absent key within that cache instance, which prevents a local cache stampede for a hot digest. Store `Arc<V>` for expensive-to-clone values. [Moka future cache docs](https://docs.rs/moka/latest/moka/future/struct.Cache.html).

Important caveats:

- Without a `weigher`, Moka assigns each entry weight 1, so `max_capacity` bounds entry count. A custom `CacheBuilder::weigher` can assign approximate payload weights and make `max_capacity` a weighted capacity (for example, estimated bytes plus fixed per-entry overhead); Moka also exposes an approximate `weighted_size`. Eviction is still best-effort, weights omit actual allocator/hash-table/runtime overhead, and `weighted_size` is approximate, so this does not enforce a hard process RSS ceiling. Use a separate process memory limit and avoid large cached bodies unless measured weights and eviction behavior meet the budget. [Moka `CacheBuilder::weigher`](https://docs.rs/moka/latest/moka/future/struct.CacheBuilder.html), [Moka cache capacity behavior](https://docs.rs/moka/latest/moka/future/struct.Cache.html).
- Singleflight applies within one process and only while initialization is in flight. Ten fleet replicas can still issue ten origin fetches on a cold key. If measurements show this is costly, add a node-local cache or short-lived distributed lease/coalescing layer; preserve bounded origin concurrency and integrity checks so a cache outage does not stampede S3.
- Cache immutable content by digest after authorization. A shared digest cache must not bypass tenant/repository authorization. Cache the bytes separately from the decision to disclose them, and re-check authorization on each read (or use explicit policy versioning and a documented revocation bound).
- Cache mutable ref heads only with short TTL or a generation-aware invalidation strategy. Never use a cached value as the compare-and-swap authority for landing or commit. Cache invalidation is an optimization, not a consistency protocol.
- Do not cache misses indefinitely. A negative entry may become stale after object publication or permission grant.

First benchmark cache hit ratio, bytes retained, clone/reference-count cost, eviction churn, same-key miss fanout, and origin calls. Only add shared/distributed caching after repeated object-store or egress costs justify operating it.

## Worker isolation and fleet growth

Ship `serve` and `worker` modes from one Rust codebase/image, with independent runtime configuration. In the first install, they can run as separate processes on the same host. The HTTP process should own interactive read/write admission and short derivations; durable background jobs (large graph/index construction, imports, repository consistency checks) belong in a bounded worker queue backed by Postgres/outbox leases, following the existing plan. This lets a small self-host deployment stay simple while large deployments add worker replicas without increasing public API CPU contention.

For organization-scale fleets:

1. Add API replicas behind an ordinary reverse proxy/load balancer; keep authorization, immutable object naming and DB transaction semantics stateless across replicas.
2. Scale workers independently by bounded queue depth/age and CPU/memory class. Use per-repository ordering/leases for operations that must serialize; do not infer ordering from process-local channels.
3. Add node/regional immutable-object caches only after origin bytes, latency, or request rates show a material cost. Make cache failure fall back through a bounded origin semaphore.
4. Partition by repository/tenant when DB connections, queue contention, or object-store traffic become measured limits. A per-process semaphore does not protect shared PostgreSQL or S3 quotas across replicas.
5. Keep per-repository hot-ref serialization and landing policy explicit. More API replicas do not make a single compare-and-swap point parallel.

This path uses basic process supervision and a load balancer; Kubernetes remains optional deployment packaging rather than an MVP assumption.

## Profiling and capacity evidence

Instrument request classes and phases with `tracing` spans: authorization, DB wait/query, object-store wait/transfer, cache hit/miss, queue wait, CPU execution, bytes, and cancellation outcome. Export distributions for p50/p95/p99 latency, admitted/queued/rejected work, active streams, upload/download bytes, CPU queue age, DB pool wait, cache entries/bytes/hit ratio, and process RSS. Use a stable high-cardinality policy: repository IDs and object hashes belong in sampled traces or logs, not unbounded metric labels.

Tokio's `tracing` ecosystem and `tokio-console` can expose task/resource behavior during diagnosis, and `tokio-metrics` collects runtime and per-task measures. Use console tooling in development/staging, and bounded-cardinality metrics in production. Profile CPU and allocations with representative repository fixtures and load mixes; a benchmark made only from tiny files will hide large-tree and merge costs. [Tokio tracing and console guide](https://tokio.rs/tokio/topics/tracing-next-steps), [tokio-metrics primary repository](https://github.com/tokio-rs/tokio-metrics), [tracing-subscriber docs](https://docs.rs/tracing-subscriber/latest/tracing_subscriber/).

Before choosing production defaults, measure at least these scenarios:

- Many small metadata/tree reads mixed with a small number of very large blob transfers.
- Cold-cache and warm-cache reads for hot objects, including concurrent first misses against multiple server replicas.
- Large upload/download with a deliberately slow client, early disconnect, timeout, and retry.
- CPU-intensive diff/merge/graph jobs competing with interactive review requests.
- Saturation at each semaphore and queue boundary, proving bounded RSS and fast rejection rather than a growing waiter population.
- Shutdown during active streams, CPU work, upload, and committed-but-unanswered mutations; confirm no partial publication and that retry reconciliation works.

Set acceptance targets from the pilot workload and host, for example a chosen p95 interactive-read objective, a maximum RSS budget, and an upload concurrency target. Record the exact CPU model, memory, object store, DB, data shape, warm/cold cache state, compiler profile and crate versions. Re-run after major dependency/runtime upgrades. Source documentation describes APIs and behavior; it does not establish Open Scion's capacity or an optimal numerical threshold.
