# Backend and storage stack research

> Historical comparison: the user subsequently selected Rust for the server. The Go server recommendation below is retained as the original research record and is superseded by the [Rust backend scaling plan](../rust-backend-scaling.md) and [updated technical plan](../technical-plan.md). Storage/correctness research remains relevant.

## Scope and assumptions

This is a planning recommendation for a small team building a self-hostable centralized online source-control service inspired by the user-visible goals in Anthropic's [source-control redesign article](https://www.anthropic.com/engineering/redesigning-source-control). It does not infer or claim anything about Anthropic's private implementation. Assume a service that stores immutable changes and file contents, exposes concurrent workspaces/branches, and supports review plus queued landing. The exact client protocol, trust model, repository scale, and interoperability requirements remain open product decisions.

## Recommendation

Start with **Go, PostgreSQL, and an S3-compatible object store**, deployed as one API/service binary plus Postgres and object storage. Keep the persistence boundary narrow enough to replace individual adapters later. Use the object store for immutable, content-addressed payloads; Postgres for repository identities, ref heads, authorization, review state, operation/event records, and derived indexes. PostgreSQL is the authority for mutable state. Do not put branch heads or ACL decisions in the object store, and do not make a distributed KV/SQL cluster the first dependency.

Go remains the pragmatic default for a small team optimizing for delivery, service operations, and maintainability. Its official documentation presents built-in concurrency and garbage collection, and a standard module system; its memory model still requires synchronization around shared mutable state ([Go docs](https://go.dev/doc/), [memory model](https://go.dev/ref/mem), [modules](https://go.dev/ref/mod)). Go's single `go` tool workflow and straightforward server deployment are a good fit for a self-hosted MVP. These are workflow considerations, not a claim that Go is categorically faster or more productive.

Rust is a sound alternative if the team already has strong Rust experience or expects the core storage/graph engine to need explicit memory control. .NET and JVM are equally serious service options where the team has operational familiarity. Zig and Swift remain possible but require more deliberate verification of server-library and deployment fit for the selected versions. No source here establishes universal productivity or speed rankings.

Use **HTTP/JSON for the initial public API** and a versioned schema. It is easy to inspect, proxy, document, and operate for browser clients and self-hosters. Keep upload/download endpoints streaming and resumable rather than encoding large blobs into JSON. If multiple first-party clients later need typed streaming RPC, add gRPC for internal or client-facing bulk transfer behind a stable domain API; gRPC uses HTTP/2 and supports bidirectional streaming ([gRPC overview](https://grpc.io/about/)). Avoid maintaining two public protocols in the MVP.

## Storage and data model

Represent all durable user-authored content as immutable objects addressed by a cryptographic digest. An object key should include a versioned hash algorithm/namespace and tenant or repository partitioning as required by the privacy model. Verify the digest and length while ingesting. Use a direct single-object path for the MVP; add chunk manifests only if measurements show large-file restart, deduplication, or streaming costs justify the extra format and retention states. Define upload resume/token/expiry behavior, hash verification, and compressed-versus-raw byte accounting as early API/storage decisions. Do not assume content hashes hide sensitive content: global deduplication can create cross-tenant existence/timing side channels. A conservative MVP scopes deduplication to a repository or tenant.

For a delta-first format, define the snapshot derivation contract explicitly. A canonical changeset records ordered parent IDs and a canonical set of file operations relative to its first parent; its ID hashes the versioned encoding of those authored fields and does not need to include a derived tree root. Applying those operations to the first parent's derived snapshot yields a deterministic tree root over entries (path bytes, modes/types, and child digests). Define deterministic byte ordering, duplicate-path rejection, empty-tree behavior, and derivation-version compatibility; do not Unicode-normalize path bytes. A tree root and its derivation/index version remain derived, versioned data. Working-copy or workspace state is an input from which a client/service constructs the changeset operations; it is not itself the authoritative branch head. Verify the derived root by reconstructing and hashing the canonical representation. The exact changeset schema and tree format must be fixed before IDs become durable API identifiers. A snapshot-first format that includes a tree root in changeset identity is a different design with different history/reconstruction tradeoffs and should be evaluated explicitly, not mixed with the delta-first model.

This follows a well-understood content-addressed shape: Git's object model stores blobs, trees, and commits as objects whose names derive from their contents ([Git Internals: Git Objects](https://git-scm.com/book/en/v2/Git-Internals-Git-Objects)). It is an analogy for the primitive, not a requirement to copy Git's format. Model changesets and tree snapshots as immutable records with stable IDs; keep mutable names such as branch heads in a separate ref table.

Store the following in Postgres:

- `repositories` and tenant/owner metadata;
- `refs(repo_id, name, target_change_id, version)` with unique `(repo_id, name)`;
- immutable changeset/tree metadata and parent edges, if small enough for queryable graph operations;
- review/change requests, approvals, checks, landing queue entries, and event/outbox rows;
- ACLs and policy versions;
- derived path/tree/commit indexes that can be rebuilt from immutable source objects.

Store immutable file objects and optionally canonical serialized tree/changeset payloads in object storage. The exact split depends on query patterns: small immutable metadata in Postgres simplifies joins and transactionality; very large trees can be serialized into object storage with searchable path summaries in Postgres. Preserve a versioned encoding and digest in either case. If chunking is adopted later, its manifest and chunk-retention model require a separate format decision.

A Postgres plus S3-compatible design is preferable to a distributed KV/SQL database for the MVP because it gives transactional refs, relational review state, familiar backup and migration operations, and self-hosting choices. Object storage offers a natural scaling boundary for large immutable payloads. AWS S3 documents strong read-after-write consistency for object PUT, overwrite, DELETE, metadata, and LIST, with atomic per-key updates ([S3 consistency](https://docs.aws.amazon.com/AmazonS3/latest/userguide/Welcome.html)). **S3-compatible does not mean every provider has identical semantics or conditional-write behavior**: validate the chosen self-hosted backend and pin the required API contract. Avoid mutable object names for correctness-critical refs; a database transaction is the ref authority.

A distributed SQL/KV system becomes worth evaluating only after a measured need for multi-region writes, storage beyond one Postgres primary's practical envelope, or independent write scaling by repository. It moves work into distributed transactions, placement, schema changes, consistency tuning, operational diagnosis, and backups. First use Postgres read replicas for read-heavy paths, vertical scaling, connection pooling, and repository partitioning/sharding at the application boundary. Partition large append-only event or audit tables only when measurements justify it; Postgres notes partitioning is most useful for very large tables with workload-aligned pruning and adds planning/maintenance considerations ([partitioning docs](https://www.postgresql.org/docs/current/ddl-partitioning.html)).

## Refs, operations, and landing correctness

Treat a ref update as compare-and-swap (CAS), never a blind overwrite. Each push/landing request supplies the expected old target (or ref version). In a transaction, lock the ref row or issue a conditional `UPDATE ... WHERE target = expected`, update its target/version, append an operation/event row, and record an outbox event. Return conflict with the current target when the predicate fails. Keep the critical section short; do object upload and expensive graph validation before it. PostgreSQL row locks block conflicting writers on the same row until transaction end ([explicit locking](https://www.postgresql.org/docs/17/explicit-locking.html)). Start with `READ COMMITTED` plus explicit CAS/row locks; use `SERIALIZABLE` only where invariant analysis and retry handling warrant it. PostgreSQL documents that serializable transactions can abort and require application retries ([transaction isolation](https://www.postgresql.org/docs/current/transaction-iso.html)).

Content objects may be uploaded before the ref CAS. That ordering means a failed CAS can leave unreferenced objects, which is safe and later handled by GC. The reverse ordering risks a committed ref pointing to absent content. Require object upload completion and digest verification before publishing a changeset/ref. A process crash between object write and SQL commit therefore leaves garbage, while a crash after SQL commit must leave all referenced content durable. Track ingest state or rely on immutable object idempotency; never treat an uncommitted DB row as proof of object durability.

Separate changeset identity from a mutable branch ref. Record every accepted state transition in an append-only operation log with actor, timestamp, request/idempotency key, old and new head, and reason. Jujutsu's public architecture is a useful implementation reference for separating immutable commit storage, operation snapshots, indexes, and refs, and its operation log supports undo/history while allowing divergent concurrent operations ([architecture](https://github.com/jj-vcs/jj/blob/main/docs/technical/architecture.md), [operation log](https://github.com/jj-vcs/jj/blob/main/docs/operation-log.md)). Adapt the separation; a centralized service should still serialize writes to a given authoritative branch head.

Landing is a policy and queue, not just a ref update. MVP semantics should be explicit: validate approvals/checks against a base head, enqueue with an expected base, then revalidate the current target and mergeability at dequeue. For an initial implementation, use a single ordered worker per repository or target branch and commit the resulting head with CAS. If another landing wins first, recompute/revalidate from the new target or mark the candidate stale and require refresh. Document whether landing preserves the submitted changeset, creates a merge changeset, rebases, or squashes. Gerrit demonstrates that these are distinct submit strategies with different resulting histories and conflict behavior ([Gerrit submit types](https://gerrit-review.googlesource.com/Documentation/cmd-set-project.html)). Do not silently mix them. This queue describes reviewed changes that are ready to land; it does not imply a core MVP requirement to accept or order offline client commits. Treat offline commit queues as a separate product capability if later requirements establish them.

A Postgres row lock serializes only the small head transition; it does not require global single-threaded landing. Queue ordering and fairness are product policy. Model dependencies explicitly if stacking is supported, and define what happens when a prerequisite fails. Keep idempotency keys so a retry after a lost response does not land twice.

## Derived indexes, authorization, and caches

Treat graph reachability, path indexes, search indexes, and review summaries as **derived, versioned data**. They must be rebuildable from immutable changesets/tree records and authoritative refs. Each index row should carry a source generation or change ID; readers must not mistake lagging derived state for authority. For correctness-sensitive operations such as deciding whether a head is an ancestor or whether a path exists, verify against the canonical graph/tree representation when the index is stale or unavailable. Build an index-repair/replay path before adding elaborate index formats.

Authorize before resolving or serving an object. A content hash is an identifier, not a capability. Every API operation should first resolve the repository/tenant and evaluate the actor's permission for that operation, then retrieve content. Cache keys for private object responses must include tenant/repository authorization scope (and relevant ACL/policy version), or use private, non-shared caches; invalidating on ACL changes is required. Do not expose distinguishable “exists but forbidden” versus “missing” behavior unless intended. Use short-lived signed object URLs only after authorization, scoped to exact object, method, and expiry. PostgreSQL row-level security can be defense in depth, but its docs note that table owners typically bypass policies, so connection roles and query paths still matter ([row security](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)).

Cache immutable objects aggressively by digest once authorized. Cache mutable ref heads only with a short TTL or generation-aware invalidation; never use a stale cache as the basis for CAS. Cache positive authorization only with policy-versioning and bounded expiry. For negative auth or nonexistent-object caching, ensure ACL grants and object arrival invalidate or expire entries correctly.

## RPC, upload, and API shape

Keep domain operations small and explicit: create repository, resolve ref, upload object/chunk, finalize changeset, compare-and-swap ref, open/update review, record checks/approvals, enqueue/land, inspect operation history. Use idempotency keys on operations with side effects. Make object upload streaming, with a finalize step that verifies the digest and writes metadata. Use pagination cursors tied to a snapshot/version for graph and review lists. Expose a stable error taxonomy (permission denied, not found, digest mismatch, stale head/conflict, invalid graph, validation pending, retryable backend failure).

HTTP APIs are adequate until measurements show that per-request JSON overhead or stream flow control is material. gRPC can then serve typed internal calls and streaming object transfer, while HTTP remains the stable integration surface. Protocol choice is reversible if domain/storage interfaces do not leak transport types.

## Crash recovery, GC, and migrations

Use an outbox table written in the same Postgres transaction as every state transition that must trigger asynchronous work (indexing, notifications, queue advancement, audit export). Workers claim rows with leases/`SKIP LOCKED`, perform idempotent work, and mark completion. On restart, expired leases become available again. This avoids the dual-write gap where DB state commits but a message publish is lost. Keep the event log sufficient to reconstruct derived indexes; outbox delivery is at-least-once, so consumers deduplicate by event ID.

Postgres WAL supports crash recovery by replaying committed changes and supports point-in-time recovery when base backups and a continuous WAL archive are available ([WAL/PITR](https://www.postgresql.org/docs/current/continuous-archiving.html)). Back up Postgres and object storage as a coordinated recovery plan: immutable objects may safely be newer than DB references, but restoring DB to a point after its objects were lost is not safe. Define RPO/RTO, verify restore procedures, and run periodic consistency scans that check every reachable object hash and length.

GC is mark-and-sweep. Mark objects reachable from all retained refs, review snapshots, tags, audit/operation retention roots, active uploads, and recovery windows. Sweep only after a grace period longer than maximum upload, replication, and backup lag. Use a two-phase process: generate a candidate deletion manifest at a fixed DB snapshot/generation, recheck liveness shortly before delete, then delete idempotently. Start with repository/tenant-local inventories and conservative retention. Object-store lifecycle expiration alone is unsafe unless the service has proved reachability and retention eligibility.

Use expand/migrate/contract schema changes: add nullable/new structures, deploy readers that accept old and new forms, backfill in bounded batches, switch writes, verify, then remove old columns/indexes in a later release. Version serialized content and API schemas independently. Avoid production startup migrations that take unbounded locks. Migration and index rebuild commands must be resumable and observable. Rehearse upgrade and downgrade/restore paths against a copy of production-scale metadata.

## Evolution path and honest limits

1. **MVP:** one Go service, one Postgres primary, S3-compatible object store, one worker pool, row-level CAS, per-target landing ordering, HTTP/JSON, append-only operations and transactional outbox. Use a single-node self-host configuration and document backup/restore. The core protocol stores immutable changesets and snapshots; it need not include a queued offline-commit workflow.
2. **Read scaling:** add Postgres read replicas for explicitly stale-tolerant endpoints, object-store/CDN delivery after authorization, and cache immutable objects. Keep branch-head reads and mutations on the primary unless replication lag is handled in the API contract.
3. **Write/storage scaling:** measure transaction latency, WAL volume, lock wait time, hot ref distribution, graph-index rebuild cost, and object-store request/egress cost. Shard by repository/tenant into independent Postgres primaries and storage buckets when a single primary becomes the measured bottleneck. Keep each repository's authoritative refs and landing queue colocated to preserve simple transactions.
4. **HA/geo:** add synchronous replicas or a managed HA Postgres arrangement for the required failure objective; add object replication and explicit regional consistency semantics. GitLab's Praefect docs illustrate that replicated repository storage requires coordination metadata and recovery procedures, and that multiple replicas trade storage for read distribution/fault tolerance ([Praefect overview](https://docs.gitlab.com/administration/gitaly/praefect/), [recovery](https://docs.gitlab.com/administration/gitaly/praefect/recovery/)). If multi-region writes become a requirement, reassess distributed SQL with workload-specific benchmarks instead of assuming it removes the need to define conflict/landing semantics.

The primary scaling limit of the recommended first version is explicit: **one Postgres primary has finite aggregate write capacity** (CPU, WAL/durability throughput, storage I/O, connection and lock-management resources). PostgreSQL supports concurrent transactions; unrelated repository/ref updates can proceed concurrently, while operations on the same ref are intentionally coordinated by CAS/row locking. A very hot branch is therefore a per-ref serialization point, not evidence that all writes on the primary serialize globally. The system does not horizontally scale arbitrary cross-repository transactions. This is a deliberate correctness/operability tradeoff, and the architecture keeps large immutable bytes and rebuildable indexes away from that write path.

## Experiments and acceptance checks before production

These are recommended validation experiments, not claims that they have been run:

- **CAS race:** run many clients updating one ref from the same expected version. Exactly one update succeeds; all losers receive a conflict with the committed head; no success response names a state that was not committed.
- **Cross-repo concurrency:** run updates to many independent refs. Confirm writes proceed in parallel and measure p50/p95/p99 commit latency, lock waits, WAL throughput, and connection saturation. Use this to set initial capacity and to expose the single-primary ceiling.
- **Crash matrix:** kill service/process at each boundary (during upload, after upload before SQL commit, after SQL commit before response, after outbox claim before ack). After restart, no ref points to missing content; unreferenced objects are recoverable garbage; outbox work is eventually replayed; retries are idempotent.
- **Landing queue:** enqueue overlapping changes against the same target, delay checks, and inject a competing update. Confirm dequeue revalidates base, resulting order follows documented policy, and each landed result has the documented first-parent/merge/rebase semantics. No approval for an old diff is silently applied to a changed diff.
- **Authorization/cache isolation:** attempt cross-tenant digest reads, guessed object IDs, revoked ACLs through warm caches, signed URL replay after expiry, and distinguishable missing/forbidden probes. No content is returned after authorization is revoked within the documented invalidation bound.
- **Index rebuild:** delete a derived index and reconstruct from canonical changesets plus operation history. Compare reachability, tree/path lookup, and ref summaries with the original. Stale indexes must never authorize a write or cause a false successful landing.
- **GC safety:** retain roots in refs, reviews, operations, active uploads, and backup windows. Verify live objects survive; only objects outside all roots and grace windows are swept. Repeat with concurrent ref publication while a mark run is in progress.
- **Storage compatibility:** run the same upload/read/overwrite/delete/list and conditional-write suite against every supported S3-compatible target. Verify strong-read assumptions before enabling any operation that depends on them.
- **Restore and migration:** restore Postgres to a point in time with its corresponding object-store snapshot/retention state, then perform a full reachable-object hash scan. Upgrade a realistic dataset through each supported migration and verify idempotent restart after interrupted backfill.

Production readiness means all correctness checks pass under injected failures, a restore meets the declared RPO/RTO, ACL/cache tests establish a concrete revocation bound, and capacity tests document when one primary requires repository sharding. Performance targets should be set from a representative workload; no universal request/throughput threshold is supportable from the available product requirements.
