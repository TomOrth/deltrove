# Rust backend operations and scaling memo

**Date:** 16 October 2026\
**Scope:** Planning follow-up to [`technical-plan.md`](../technical-plan.md), with Rust selected for the server. The existing Go CLI remains unchanged. No code or measurements were produced here.\
**Assumption:** Small-team self-hosting comes first; each scaling step must have an observable reason and a rollback path.

## Recommendation

Build one Rust executable with `api`, `worker`, and optional `cache` process modes. Keep the API stateless apart from bounded per-process caches; keep Postgres authoritative for refs, permissions, jobs, operation outcomes, and derived-index generations; keep immutable payloads in object storage. The modes can ship in one OCI image and run as one process for a small install, then be deployed and scaled independently. Cache mode is an optional accelerator with bounded memory/disk and authorization-scoped keys. Cache loss or bypass must affect latency and object-store load only, never correctness. Do not require a cache cluster for an MVP installation.

Use Postgres-backed at-least-once jobs before adding a broker. Claim short batches with `FOR UPDATE SKIP LOCKED`, assign a lease deadline and monotonically increasing claim/fencing generation, and commit the claim before doing work. PostgreSQL explicitly limits `SKIP LOCKED` to queue-like access because skipped rows produce an inconsistent general-purpose view. A lease timeout permits another attempt; it does not stop a paused former worker from resuming. Every final database write must therefore check the current generation/token and expected job state. Make handlers idempotent by job/event ID, and make external effects either immutable/idempotent (content-addressed object put) or outbox-driven. A stale worker must be unable to publish a ref, index generation, or completion result after a newer claim. Client mutation idempotency keys should map to a durable stored outcome committed in the same transaction as the mutation, so retries after a lost response return the original result.

For protected branch landing, preserve the existing plan's per-target ordering and short Postgres CAS transaction. Separate queue admission, expensive candidate construction and checks, and final policy/ref validation. Scale independent repos and refs concurrently; serialize the final update to the same ref. API replicas or more Tokio tasks do not remove this coordination point or increase one Postgres primary's write capacity without limit.

## Service objectives and scale triggers

Treat the following as **pilot starting objectives**, not research facts or promises. Choose a 28-day window and measure from the client-visible API boundary; exclude caller cancellation and explicitly bounded large/bulk operations from interactive latency objectives. Tune once representative users and repository shapes exist.

| Signal | Pilot objective / action |
| --- | --- |
| Interactive read availability | 99.5% of valid, authorized, non-bulk requests succeed over 28 days. Alert on fast error-budget burn; investigate dependency failures separately from caller errors. |
| Interactive read latency | For bounded tree/ref/file metadata reads on warm and cold caches, p95 under 300 ms and p99 under 1 s at the declared pilot load. Publish limits by route and payload class. |
| Mutation latency | 99% of accepted small mutations reach a durable API outcome within 2 s, excluding upload transfer and asynchronous review/landing work. Unknown client outcomes are recoverable by idempotency key. |
| Job freshness | p95 age of ready derivation/index jobs under 60 s during normal load; page/notify operators only if oldest-ready age stays above 5 min or grows for 10 min. Landing wait-for-check time is reported separately. |
| Recovery | Start the pilot with explicit operator-approved targets such as metadata RPO <= 5 min and service RTO <= 4 h. Test them. Object retention must make every object reachable from any supported restored database point available. |

These targets are intentionally modest hypotheses for a self-hosted pilot. Do not advertise them as an SLA until measurement, backup policy, and installation topology support them. Google SRE's guidance supports distinct user-facing objectives and error budgets, not any particular thresholds for this product.

Scale API replicas when route-level latency/error SLOs breach under load and API CPU, memory, file descriptors, or connection-pool saturation point to the API tier; first check downstream wait. Keep each replica's DB pool within a global Postgres connection budget and use a pooler where appropriate. Scale worker replicas or bounded concurrency when oldest-ready job age/backlog exceeds its objective while DB/object-store headroom remains. Add worker classes/queues before indiscriminately increasing concurrency, so expensive merge/index jobs cannot starve small derivations. Add or enlarge the cache only when measured hit rate and avoided object-store bytes/latency justify its memory and invalidation burden. If database CPU, WAL/fsync throughput, I/O, lock wait, or connection pressure is the constraint, adding API/worker replicas may worsen it; tune queries/indexes, cap concurrency, batch carefully, and scale the Postgres primary vertically before considering repository sharding. A read replica helps only endpoints whose consistency contract tolerates lag.

Operational dashboards should include request rate/errors/latency by bounded route class; upload bytes and checksum failures; DB pool wait, transaction latency, WAL rate, lock waits/deadlocks, replication lag; per-queue ready count and oldest-ready age, attempts/lease expirations/stale-token rejects; object-store latency/errors/bytes; cache hit/miss/eviction; process RSS/CPU, Tokio runtime queue/busy metrics; and backup age, WAL archive gap, last successful restore drill, and reachable-object scrub status. Avoid repository IDs, object hashes, paths, users, or raw error text as high-cardinality metric labels. Put those in sampled, access-controlled traces/logs with redaction.

## Rust observability and profiling

The Rust observability stack is usable for production, with a maturity caveat: the OpenTelemetry Rust project currently reports traces as beta and metrics/logs as stable. Use `tracing` spans/events as the application instrumentation surface, `tracing-subscriber` for structured logs/filtering, `tracing-opentelemetry` and OTLP export for distributed traces, and stable OpenTelemetry metrics or a Prometheus exporter for operational counters/histograms. Pin a compatible crate set and collector/exporter versions; keep telemetry failure non-fatal and bound queues/batches. Instrument request/trace context across API, outbox/job attempts, database calls, and object-store calls. Never put source contents, secrets, signed URLs, or unbounded object/repo identity in telemetry.

Tokio runtime metrics are available via `tokio-metrics`; some additional runtime metrics require Tokio's `tokio_unstable` build cfg, so do not make those a release requirement before verifying compiler/version support. Use the stable subset first and add per-queue/service metrics at the application layer. For CPU profiling, start with OS `perf`/flamegraphs in controlled Linux staging and evaluate `pprof-rs` only after platform and signal-safety review; its own documentation notes limitations in unwind safety and that it focuses on CPU profiling. Profiling endpoints/data must be opt-in, authenticated, and unavailable to public clients. Benchmark optimized release builds with production-like symbols/configuration, then profile an identified regression rather than continuously sampling every production process by default.

## Correctness and failure testing

- **Property tests:** use `proptest` for canonical encodings, path ordering/round trips, tree derivation invariants, upload resumptions, idempotency and replay. Compare generated operation sequences against a simple reference model. Shrinking is useful for reducing discovered counterexamples; it does not establish completeness.
- **Loom:** reserve for small in-process synchronization primitives (e.g. cache publication, local generation swaps, cancellation state) that use Loom replacement synchronization types. Loom explores bounded memory-model interleavings, but it cannot see ordinary synchronization primitives not replaced by its modeled types; it does not model Postgres, object stores, processes, or network partitions. It is not the main lease/fencing proof.
- **Async/system simulation:** use deterministic async tests with Tokio paused time and explicit barriers for lease expiry, heartbeat, cancellation, retries, and shutdown sequencing. Evaluate Turmoil for protocol-level multi-host simulations of partitions/held messages and worker restart; it requires adapters because the production app must swap Tokio network types for simulated ones, and its filesystem support is documented unstable. Treat simulation as complementary to real integration tests.
- **Fault injection:** run API and multiple worker replicas against real Postgres and the chosen object-store implementation. Crash or pause a worker after claim, after immutable object write, before/after DB commit, and before acknowledgement; expire a lease while the first worker is paused; deliver duplicate/out-of-order outbox events; cut DB/object/network access; and restart during graceful shutdown. Assert stale fencing tokens cannot publish, retries converge to one logical result, no ref names missing content, and acknowledged outcomes can be looked up.
- **HA/upgrade tests:** repeatedly terminate an API and worker during rolling deploy, fail over Postgres, and exercise object-store outage/restore. Test old and new binaries against expanded schema and mixed object-format readers before switching writers. Verify rollback while new-format writes are disabled, and forward recovery after they begin.

Loom and Turmoil are helpful but narrow tools. Distributed correctness still depends on the database transaction protocol, object-store contract, process-level fault tests, and restore rehearsal.

## Upgrades, recovery, and the single-repository ceiling

Use expand/migrate/contract releases. Run bounded, resumable schema migrations as a separate operator-controlled command/job, not synchronously at every API startup. First add compatible nullable columns/tables/indexes; roll binaries that read old and new; backfill; switch writes behind a feature gate; verify counts/invariants; only then stop writing old representation and remove old schema in a later release. Ensure N and N-1 binaries tolerate the expanded schema during rolling deployment. Version API, canonical object encodings, derived indexes, and cache entries independently. Readers should support the old durable object version for at least the defined backup-retention/restore window. Deploy code capable of reading a format before any writer emits it. Never use rolling restarts as a substitute for an explicit format migration protocol.

Keep Postgres PITR/WAL and object retention coordinated with a recovery watermark plus immutable object manifest. Restore to an isolated environment, restore the matching database point, ensure all referenced objects exist, then run schema/version checks and full reachable-object digest/length scrub before routing traffic. Newer unreferenced immutable objects are tolerable; missing bytes for a restored committed ref are not. A restore may require object versions or retained objects from *before* the database target time, so the DB timestamp alone is not a sufficient object restore selector. Rehearse the whole process and record elapsed time. Postgres documents PITR via base backup plus a continuous WAL sequence; it does not provide the cross-system atomicity for Postgres plus S3-compatible storage.

One primary can serve concurrent transactions on independent repositories, while a hot ref serializes its own CAS/landing transition. Horizontal replicas scale stateless API reads and independent job execution only within DB/object-store budgets. Repository/tenant sharding can distribute many repositories across primaries while keeping each repo's transaction boundary local. It cannot split a single enormous/hot repository across primaries without a new consistency and graph-placement design. The hot-repo gate is measured: graph/path query work, index size/rebuild time, hottest-ref queue age, DB CPU/WAL/lock waits, and object fan-out. If a representative single-repo workload violates targets after query/index/cache and vertical headroom work, pause the scale-out promise and prototype repository-local graph/index partitioning or a new storage design. Do not cite API replica count as evidence that a monorepo scales.

## Benchmark and decision experiments

Build a repeatable workload corpus with small/medium/large repositories, varying object bytes, tree entries, history depth/fan-out, path count, sparse selection, branch count, and hot-ref share. Preserve realistic skew and change sizes. Test cold/warm cache; read-heavy browsing; concurrent uploads/commits; history/tree/diff; landing with slow checks; and mixed workload. Report p50/p95/p99 latency, throughput, errors, queue age, DB lock/pool/WAL metrics, memory/CPU, object-store calls/bytes, cache hit rate, and recovery after burst. Fix hardware, Postgres/object-store versions, data set, deployment topology and load generator; warm up, repeat runs, compare confidence intervals, and retain raw results/config. Use Criterion for isolated encoding/tree/diff primitives, but use an end-to-end load driver for API capacity. No Rust-vs-Go speed claim follows from a microbenchmark.

Specific experiments before HA claim: (1) lease-expiry race with old worker pause/resume and a newer token; (2) two+ worker replicas draining a burst while measuring starvation and DB contention; (3) same-ref CAS contention versus many independent refs, measuring serialized fraction; (4) API replica scaling until Postgres saturation is visible; (5) kill/failover matrix across object put, SQL commit, outbox ack, and response; (6) restore a DB point while retaining object versions and scrub every reachable object; (7) N/N-1 rolling upgrade and rollback before/after enabling a new object format; (8) single-hot-repo benchmark at increasing history/path dimensions, explicitly identifying the point where indexes or primary capacity miss targets.

## Uncertainties

No request distribution, repository corpus, cloud/self-hosted topology, Postgres version, S3-compatible implementation, or team Rust experience was provided. The SLO numbers and scale thresholds above are testable starting proposals only. Rust OTel traces remain beta per the official status page at this review date; crate compatibility and exporter behavior must be pinned in implementation. Turmoil adapters and coverage are not yet known. A production HA design still needs a chosen Postgres failover mechanism, object-store durability/consistency contract, explicit RPO/RTO, and successful restore/upgrade drills.
