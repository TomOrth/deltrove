# F0 acceptance contract

**Status:** proposed contract; maintainer acceptance is pending. No product implementation, product acceptance test, performance benchmark, durability qualification, threat review, or pilot measurement is represented as complete. This document is A02 and depends on the A01 workload fixture draft. It is reconciled to [A01 workload fixtures](workload-fixtures.md) and manifest [`fixtures/workloads/manifest.json`](../../fixtures/workloads/manifest.json), seed **2301**, default and extended shapes below. These are synthetic inputs, not pilot observations.

F0 fixes what later evidence must prove. It does not select an orchestration engine, promise host/site HA, set customer capacity, or silently expand Git compatibility. The roadmap remains authoritative for milestone ordering and release gates: F0 acceptance requires A01/A02; F1 requires A03–A07; private alpha requires M1–M4 and M7's minimum install/backup/restore subset; the small-team release requires M1–M8; enterprise readiness is a separately qualified S1–S8 program.

## How to read the requirements

`Spec check` means a documentation/contract review that can be done now. `Product test` means future executable evidence; every such test is **NOT RUN** until implementation exists and the named environment/evidence is recorded. Passing a spec check never substitutes for a product test. A release row is an entry condition, not a claim that this document passes it.

Use the fixture IDs `tiny-graph` (5-node graph), `wide-tree` (64 files), `deep-tree` (depth 24), `binary-mix` (8 deterministic 1 KiB blobs plus marker), `many-repos` (8 repositories), `hot-repo` (256 files), and `long-ci-waits` (12 simulated waits). The shared A01 generator records seed 2301 and content hashes. Its opt-in extended ceilings are 4,096 wide files, depth 128, 64 binary blobs, 256 repositories, 16,384 hot-repo files and 1,000 wait records. Bind scenarios to these exact manifest profiles and record counts, hashes, topology, versions, exact command, raw results and limitations. Fixture labels and sizes are not measurements. Use real pilot repositories only with permission and record observed properties separately from synthetic assumptions.

## Durability and failure profiles

An acknowledgment means the authoritative operation outcome and every object it references satisfy the configured profile. PostgreSQL and object storage do not share a physical transaction: durable immutable object writes precede atomic SQL publication of membership, pins, outcome and outbox. Unpublished object orphans may remain for conservative collection; a published reference to missing bytes is forbidden. Derived data may be pending, but readers must report pending/failed rather than substitute another revision.

| ID / profile | Must survive | May be lost / service behavior | Minimum proof and current status |
|---|---|---|---|
| DP-01 / Process restart (alpha/MVP baseline) | Every acknowledged mutation, object membership, idempotency outcome and recoverable workspace journal when underlying durable volumes survive. Retry returns the same outcome; no partial publication. | In-flight unacknowledged work may require retry/reconciliation. Local caches may be rebuilt; dirty working files/preimages may not be discarded. | `durability_process_restart`: crash at object write/flush, SQL publication/commit, response, derivation, landing and each workspace journal boundary; restart and compare independent ledger/reachable objects/files. **NOT RUN.** |
| DP-02 / Host/volume loss (not implied by alpha/MVP) | No guarantee in single-node profile. A deployment may claim host-loss survival only after S1 establishes independent synchronous metadata and replicated object copies, safe promotion and fencing. | Single-node installation may be unavailable and may lose state with its host/volume. Never silently acknowledge using async fallback under a no-loss profile. | `durability_host_loss`: remove one declared failure domain during acknowledged writes; unavailable required synchronous copy blocks acknowledgment; verify eligible promotion and old-primary fencing. **S1 NOT RUN; no HA claim.** |
| DP-03 / Site loss / disaster recovery (separate enterprise objective) | Only records/objects proven present in the selected coordinated recovery points. Advertised RPO/RTO must come from a completed drill. | Wider multi-copy/site loss has no default zero-loss guarantee; async replication lag is not a hard RPO. Service stays fenced until restore and reconciliation complete. | `durability_site_restore`: restore DB, object manifest/bytes and selected workflow state into clean environment with misaligned points; verify retained digests, fresh non-reused epoch, stale callback rejection, measured loss/time. **S7 NOT RUN; targets unset.** |

## Initial threat model

This is an initial boundary inventory for F0, not a completed security review. The default trust boundary is repository tenant and authenticated actor; bytes, paths, callbacks, clients, caches, workers and external runners are untrusted inputs. Product controls below are acceptance requirements, not evidence they exist.

| ID / threat / asset | Required control and named oracle |
|---|---|
| TH-01 / Cross-repository digest guessing, cache leakage, revoked access, stale replicas | Authorize every repository operation and object membership on cache hits; primary/read-after-write or explicit watermark. `security_cross_repo_cache_revocation` asserts guessed digest and warm-cache read fail after revoke. **NOT RUN.** |
| TH-02 / Malicious path, symlink escape, case/Unicode alias, repository-controlled source/filename/comment | Validate repository-relative path bytes and host representability before writes; never follow symlink targets; escape source and render as text, do not execute repo HTML/SVG/Markdown HTML. `security_path_and_rendering` traversal/collision corpus plus browser XSS fixtures. **NOT RUN.** |
| TH-03 / Forged/stale CI callback, self-approval, policy or permission race | Authenticated scoped producer; bind result to exact candidate/run; final serializable transaction rechecks policy, approval, check, target generation and authorization. `security_landing_races` races revoke/check/policy changes against landing. **NOT RUN.** |
| TH-04 / Compromised runner or workflow/worker replay | CI runners receive no service credentials; scoped checkout token, stable request identity, bounded logs/artifacts, lease/fence/recovery-epoch checks on publication. External effects may duplicate unless provider idempotency is proven. `security_runner_replay` duplicates/stales callbacks and pauses old worker through takeover. **NOT RUN.** |
| TH-05 / Denial of service through uploads, wide/deep graphs, huge diffs, slow clients, long waits or cancellation | Enforce quotas and limits for bytes, CPU, queue, retained buffers, response lifetime, jobs, history and DB connections; cancellation of HTTP does not imply CPU termination. `security_resource_bounds` uses `wide-tree`, `deep-tree`, `binary-mix`, `long-ci-waits`, oversized payloads and slow consumers; assert bounded resources and explicit rejection. **NOT RUN.** |
| TH-06 / Secret/token disclosure in logs, URLs, workflow history or browser storage | Scoped expiring credentials; no secrets/source blobs in workflow inputs or logs; no public cache directives or MVP presigned URLs; secure same-origin session/CSRF policy. `security_secret_scan_and_session` inspects captured logs/history and exercises session/CSRF cases. **NOT RUN.** |
| TH-07 / Corrupt/poisoned object or derived cache/index | Verify digest, length, type, repository membership and derivation version; cache never authorizes or redefines canonical identity; rebuild indexes and compare logical snapshot. `security_corrupt_object_cache` injects truncation, digest mismatch and poisoned cache. **NOT RUN.** |

Path-level ACLs, arbitrary hooks/filters, browser-to-local-daemon access, shared cross-tenant cache, and offline queued server commits are outside the initial acceptance boundary. If introduced, each needs a new explicit threat review and feature gate.
